# Apple Intelligence 端侧模型在 ANE 上的部署（M4）

- 日期：2026-10-09
- 机器：M4 MacBook（h16g），macOS 27.0.0
- 数据：`data/12_apps/afm/`（我们的测量：非 root 与 root 下的 anemon 记录、生成速度）
- 工具：`tools/12_apps/fmprobe.swift`（用公开的 FoundationModels 框架调用系统端侧模型）、`tools/12_apps/fmprobe_root.sh`（root 下的 anemon 加 7 轮生成）
- 模型文件的原始提取（函数表、HWX 解析、资产清单）在 `private/apple_intelligence/`，不进仓库

## 1. 结论

1. Apple Intelligence 的端侧语言模型跑在 ANE 上。模型资产的元数据写明 `model_type = ane`，唯一的执行程序是一个 H16 代的 HWX（`cputype 0x80`、`cpusubtype 7`）。实测生成期间 ANE 的 DRAM 读流量稳定在约 30 GB/s，生成一结束立即归零（第 6 节）。
2. 它不经过 aned 的编译缓存。ANE 程序由 Apple 预先编译好，随系统资产下载；资产名都带 `H16G`，即按芯片的 ANE 架构分别构建。所以第 5 章所述的首次加载编译开销对它不存在，aned 缓存里也看不到它。
3. 所谓"3B 模型"是一个稀疏模型：44 个稀疏层每层有 380 个宽 256 的前馈专家，按 2 位存储，稀疏前馈部分总计约 197 亿参数（4.93 GB）；运行时只把选中的 5、14 或 23 个专家换入 ANE 可见的权重区。产品里的 1B、2B、3B 是同一个基础模型按这三档稀疏度运行。
4. 解码每个词元从 DRAM 读约 0.73 GB，约为"稠密权重加当前激活专家"各读一遍的量。这与第 9、10 章的结论一致：端侧解码受读权重带宽限制，Apple 的做法是减少每个词元要读的权重（2 位量化、只激活少量专家），而不是增加算力。推测解码也已启用，但在开放式写作中每次验证平均只接受约 1.5 个词元（第 6.1 节）。
5. ANE 平均功耗约 1.7 W，每个词元 ANE 约 41 mJ；为 ANE 调度的主机 CPU 另耗约 37 mJ，与 ANE 本身相当（第 6.1 节）。

位置：`/System/Library/AssetsV2/com_apple_MobileAsset_UAF_FM_GenerativeModels/`，共 106 项、约 21 GB，均为签名的 cryptex 磁盘映像。主要部分：

| 类别 | 内容 | 大小 |
|---|---|---|
| 3B 基础模型 | `instruct_3b.base.generic_sparse`，版本名 `afmplus-v11.2-ifp`，上下文 8192 | 12 GB（映像与展开内容各约 6 GB） |
| 功能适配器 | 约 30 个 LoRA（秩 48），如摘要、邮件回复、校对、翻译、提醒事项、照片回忆、图乐园、快捷指令、Foundation Models API | 每个约 98 MB |
| 草稿模型 | 与各功能适配器成对，名字带 `draft`，配置 `v11-ifp-9m`，用于推测解码 | 每个约 98 MB（含 35 MB 的 odix） |

## 3. 基础模型的结构

由 `odix` 函数表里的张量名和 IFP 权重文件头部得出（均为文件中的字段，不是推算）：

| 项目 | 值 |
|---|---|
| 隐藏维度 | 1536 |
| 注意力投影 | Q 1536→2048，K、V 1536→1024，输出 2048→1536 |
| 层数 | 56 层：12 层稠密层，23 层稀疏层，21 层"KV 复用"稀疏层 |
| KV 复用层 | 只有 Q 投影，没有 K、V 投影，复用前面层的 KV 缓存；21/56 = 37.5%，与 Apple 2025 年技术报告所述 KV 缓存减少 37.5% 相符 |
| 稠密层前馈宽度 | 3072 |
| 稀疏层 | 44 层，每层 380 个专家，每个专家宽 256，含门控、上投影、下投影 3 个矩阵 |
| 稀疏权重格式 | 2 位，查找表为 fp16 的 −1.5、−0.5、0.5、1.5；另有逐通道的 fp16 缩放 |
| 三档稀疏度 | ifp1、ifp2、ifp3 分别激活 5、14、23 个专家，有效前馈宽度 1280、3584、5888；默认 ifp3 |
| 专家选择 | 单独的小程序 `project_experts`（卷积加逐元素运算，即线性路由），配置项 `expert_selection_frequency = 32` |

由此估算的参数量：注意力约 4.6 亿，稠密前馈约 1.7 亿，稀疏前馈总计约 197 亿，ifp3 档每次激活约 11.9 亿；另有词表嵌入（大小未读出）。按此估算，ifp3 档的激活参数约为 20 亿加嵌入，比"3B"的名字小；名字的来历未知。

`IFP` 的写法与 Apple 发表的 Instruction-Following Pruning（按指令选择要激活的前馈单元）一致，但文件里没有出现这个全称，属于推测。

## 4. ANE 程序

基础模型的执行程序是 `main-h16g-delegates/MPSGraph/…/binary_0.hwx`（662 MiB），由 MPSGraph 的 ANE 委托执行；`main-h16g.odix`（250 MB）是外层的计算图容器，文件头为 `odix`，由私有框架 ODIE 解释。

编译信息（HWX 的 `LC_IDENT`）：ANE 编译器 v10.25.2，`-t h16g`，关闭双引擎（`--fdisable-bonded-networks=true`），L2 常驻（`--fl2-cache-mode=resident`），开启 `kernel-rewind`，`memcache-size` 为 4 MiB。

各段：

| 段 | 大小 | 文件中有数据 | 含义 |
|---|---|---|---|
| `__TEXT` | 210 MiB | 是 | 指令流 157 MiB，常量 53 MiB |
| `__KERN_0`–`__KERN_3` | 共 439 MiB | 是 | 固化的权重（稠密层、注意力等） |
| `__MKERN_6`、`__MKERN_28`、`__MKERN_40`、`__MKERN_74` | 131、29、243、355 MiB | 否 | 运行时写入的权重槽 |

IFP 元数据文件中的尺寸字段与 MKERN 段的大小逐字节相等：ifp1 的 0x82bc000 等于 `__MKERN_6`，ifp3 的 0x16284000 等于 `__MKERN_74`。所以 MKERN 段就是存放当前选中专家的槽，每档稀疏度一个。ifp3 的槽平均每个专家每层 367 KB，比纯 2 位数据（295 KB）多约 25%，多出的部分应为缩放和对齐。

函数表按"阶段 × 上下文长度 × 每次处理的词元数"展开：`prompt_opt`（处理提示词，分 `dense_only` 和 `sparse_only` 两部分）与 `extend`（生成），上下文档位 256–8192，每次 8、16 或 64 个词元，三档稀疏度各一套，另有文本与音频的嵌入和 logits 函数。每次 8 个词元的 `extend` 对应推测解码：草稿模型的 `draft_steps = 7`，大模型一次验证 8 个位置。

草稿模型的 HWX 只有 10 MB，其中权重段 4.7 MB，配置名中的 `9m` 应指约 900 万参数。

## 5. 运行时

调用链：`TGOnDeviceInferenceProviderService`（以 `_modelmanagerd` 身份运行）→ TokenGenerationInference → ODIE、ODIEDelegates → MPSGraph → ANE。空闲时推理服务只占约 3 MB 内存，模型按需加载。

## 6. 实测

用 `fmprobe` 连续生成 4 次同一篇约 370 词的短文（贪心采样），同时用非 root 的 `anemon --json --interval 1` 记录（`data/12_apps/afm/`）：

| | 空闲（20 个采样） | 生成中（42 个采样） |
|---|---|---|
| ANE 读 DRAM | 0 | 30.6 GB/s |
| ANE 写 DRAM | 0 | 0.57 GB/s |
| ANE 中断 | 0 | 629 次/秒 |
| 主机 CPU 功耗 | 1.19 W | 2.59 W |
| ANE 功耗（SMC 估计） | 0 | 中位数约 1.2 W，单次读数在 0.2–6.8 W 之间跳动 |

- 生成速度 41.3–42.9 词元/秒（每次 486 个词元），首词元延迟 0.33 s；第一次为冷启动，首词元延迟 0.93 s（另一次冷启动为 1.87 s）。
- 每个词元读约 30.6 / 41.7 ≈ 0.73 GB。ifp3 档的固化权重与专家槽合计约 0.84 GB，量级相当。
- 这一轮的功耗读数不可靠：M4 的 SMC 电源轨每秒更新一次，需要至少约 60 s 的连续负载，这里每次生成只有约 12 s。

### 6.1 root 下的 anemon：按程序拆分

用 `tools/12_apps/fmprobe_root.sh` 连续生成 7 轮（约 82 s 的负载，前后各空闲 15 s），root 下的 anemon 每秒记录一次（`data/12_apps/afm/anemon_root_fmprobe.jsonl`）。生成速度与上一轮相同，41.5–41.8 词元/秒。本机此前睡眠过，busy % 来自驱动事件（`ane_busy_source = host`），精度低于内核时间戳。

负载期间（76 个采样）的中位数：ANE busy 80%，任务 153 个/秒，读 DRAM 30.6 GB/s，内存时钟档位 F4，没有降频。按 ANE 程序（anemon 的 handle）拆分，取整段的平均：

| 进程 | 程序 | 任务/秒 | 每任务 ms | 占用 ms/s | 推断 |
|---|---|---|---|---|---|
| 推理服务 A | 1 | 28.1 | 24.3 | 682 | 3B 基础模型的验证（`extend`，每次 8 个位置） |
| 推理服务 A | 2 | 26.4 | 3.2 | 85 | 每次验证配一次，可能是 logits 或嵌入 |
| 推理服务 A | 3 | 101.0 | 0.26 | 26 | 草稿模型（约 900 万参数）的逐步生成 |
| 推理服务 B | 4 | 9.7 | 6.8 | 66 | 另一个推理服务实例，可能是输出的安全分类 |
| 推理服务 B | 5 | 0.9 | 6.5 | 6 | 偶发 |

两个推理服务都是 `TGOnDeviceInferenceProviderService`，用户进程 `fmprobe` 自己不提交 ANE 任务。"推断"一列由每秒次数和每次时长对应而来，未与函数名逐一核对。

由此得出：

- 推测解码确实启用，但接受率不高：大模型每秒验证 28.1 次、产出 41.6 个词元，平均每次验证只接受约 1.5 个词元（草稿每次最多给 7 个）。这次的提示词是开放式写作，草稿模型较难猜中；摘要等任务的接受率可能更高。
- 每次验证 24.3 ms。如果这期间的 DRAM 读流量主要来自它，每次验证约读 30.6 / 28.1 ≈ 1.09 GB，大于 ifp3 档的权重 0.84 GB，多出的部分可能是 KV 缓存和词表矩阵。按此估算，验证时的读带宽约 1.09 GB / 24.3 ms ≈ 45 GB/s，约为 anemon 测得的 M4 ANE 读带宽上限 65 GB/s 的 70%。
- ANE 功耗（82 s 窗口）：平均 1.70 W，中位数 1.34 W，第 10 到第 90 百分位为 0.32–3.44 W；主机 CPU 额外功耗平均 1.52 W。按平均值折算，每个词元 ANE 约 41 mJ、主机 CPU 约 37 mJ：为 ANE 调度的 CPU 能耗与 ANE 本身相当。
