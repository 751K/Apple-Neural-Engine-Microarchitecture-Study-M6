# M6 计算阵列微基准（清单 B 组）

- 日期：2026-10-02
- 工具：
  - `tools/common/chain.py`：生成卷积链（共享权重，或每层各自的权重 `_u`）；
  - `tools/common/runall.sh` + `tools/common/bondrun.m`：计时，并记录每个 ANE 的中断。
- 原始数据：`data/05_compute/chains_run2.txt`、`data/05_compute/b2b_run.txt`

## 0. 计时方法上的两个坑

1. **每次调用有约 160 µs 的固定下限。** 小于这个量的 ANE 工作会被完全"藏"在下限里：C ≤ 256、宽 128 的 1×1 链，32 层和 96 层耗时几乎一样。所以斜率法必须让总工作量明显超过这个下限。
2. **ANE 从空闲到满速有约 0.3 s 的爬升。** 从空闲开始连续调用，前约 200 次（每次约 1.4 ms）逐渐降到稳定的约 0.5 ms，相差 **2.8 倍**。推测是 SoC 电源管理在爬升 ANE 的时钟。
   - `bondrun` 一开始把"空闲 0.5 s 基线"放在预热之后，导致每次测量开头都重新爬升，中位数被拉高。现在已把基线移到预热之前，并且预热至少 1 s。
   - 修正后重测，单 / 双 ANE 的结果（`bonded_measure.md`）没有变化：那组模型每次调用时间长、次数多，受影响很小。

## B4 / B5：卷积核尺寸、Winograd

256 通道，空间 8×16（128 个像素，单 ANE），用 L=16 和 L=48 的斜率：

| 核 | 每层耗时 | 每层 FLOP（名义值，含 padding） | 边际吞吐 |
|---|---|---|---|
| 1×1 | 0.59 µs | 16.8 M | 不可靠（总时间接近下限） |
| 3×3 | 9.9 µs | 151 M | 15.3 TFLOPS |
| 5×5 | 24.8 µs | 419 M | 16.9 TFLOPS |
| 7×7 | 42.3 µs | 822 M | 19.4 TFLOPS |

- 都没有超过单 ANE 的约 20.6 TFLOPS。若启用了 Winograd F(2×2,3×3)，3×3 的有效吞吐应该是直接卷积的约 2.25 倍。所以**在这个形状下没有用 Winograd**。
- 核越大，效率越接近峰值。3×3 只有约 74%，可能和空间太小（8×16）时的边缘 / padding 有关。

## B6：按链深度的吞吐（对照 maderix 的 M4 表）

512 通道，32×32，每层权重各不相同（`_u`）。这个形状在 M6 上被切到两个 ANE（两边中断次数相同）。吞吐包含每次调用的固定开销，和 maderix 的口径一致。

| 层数 | M6 中位数 | M6 FP16 TFLOPS | maderix M4 FP16 TFLOPS |
|---|---|---|---|
| 1 | 192 µs | 2.8 | 5.4 |
| 4 | 242 µs | 8.9 | 9.8 |
| 8 | 340 µs | 12.6 | 12.3 |
| 16 | 410 µs | 21.0 | 11.7 |
| 32 | 900 µs | 19.1 | 16.1 |
| 48 | 1005 µs | 25.6 | 18.5（1024 通道、64²） |

- 层数少时 M6 并不比 M4 快（受固定开销限制）；16 层起明显更快，48 层约为 M4 的 1.4 倍。
- 32 层反而比 16 层效率低（900 µs，每次调用 2.0 个中断，而 16 层是 3.1 个）。原因已查明，见下面 B6b：**Core ML 在 32、34 层把最后一个 relu 放到了 CPU 上**，和权重大小无关。

### B6b："32 层反常地慢"的原因（2026-10-02）

- 细扫（`data/05_compute/b6x_sweep.txt`）：同一形状，层数 16–64，每层权重各不相同和共享一份权重各测一组，两轮。两组曲线几乎重合（共享权重的只慢 10–15 µs），**和权重总量无关**。
- 36 层起是直线：约 382 µs + 每层 13.25 µs（约 40.5 TFLOPS）。偏离直线的是两个独立效应：

| 层数 | 16 | 20 | 24 | 28–30 | **32** | **34** | 36–64 |
|---|---|---|---|---|---|---|---|
| 每次调用 | 410 | 540 | 654 | 754–781 | **905–912** | **934** | 在直线上 |
| 偏离直线 | −184 | −107 | −46 | 0 | **+99** | **+102** | 0 |

- **用固件任务时间戳拆分**（`tools/05_compute/b6_ktrace.sh`，root；`tools/05_compute/b6_split.py`；数据 `data/05_compute/b6_kt/`）：

| 层数 | ANE 任务时长 | 任务比直线多 | 任务结束 → 下次提交（主机侧） |
|---|---|---|---|
| 16 | 230 µs | −7 | **166** |
| 20 | 283 | −7 | 246 |
| 24 | 339 | −5 | 308 |
| 28 / 30 | 397 / 421 | +1 / −2 | 350 / 353 |
| **32 / 34** | 470 / 494 | **+21 / +18** | **443 / 440** |
| 36–48 | | 0 | 353–356 |

  ANE 任务时长 = 25.5 + 13.24·L µs。
- **效应 A（层数少时比直线快）全在主机侧，是 CPU 空闲电源管理造成的唤醒延迟**：任务结束后的那段从 166 µs 逐步涨到 350 µs（28 层后稳定），ANE 本身没变。和 memory.md C2j 是同一个机制，这里看到的是从浅睡到深睡逐步加深的全过程。证据：
  1. **阶段拆分**（`tools/05_compute/effA_ktrace.sh`，root；`tools/05_compute/effA_stages.py`；数据 `data/05_compute/effA_kt/`），中位数 µs：

     | 层数 | 结束→固件发消息 | 消息→中断 | 中断→完成标记 | 驱动完成处理（00a0→0170） | 用户线程唤醒返回（0170→0024） | 返回→下次提交 | 合计 |
     |---|---|---|---|---|---|---|---|
     | 16 | 40.0 | 6.8 | 5.2 | 38.9 | 65.5 | 4.5 | 161.9 |
     | 20 | 44.5 | 8.7 | 8.2 | 73.1 | 103.6 | 5.1 | 244.7 |
     | 24 | 40.6 | 10.0 | 9.8 | 102.9 | 139.9 | 5.4 | 311.5 |
     | 28 | 38.1 | 12.8 | 11.2 | 123.0 | 161.4 | 5.6 | 355.4 |
     | 36 / 48 | 42.3 / 38.4 | 12.3 / 12.5 | 11.9 / 11.4 | 120.2 / 120.4 | 163.3 / 162.2 | 5.8 / 5.9 | 358.9 / 356.2 |

     固件那段不变；增长的约 194 µs 中约 178 µs 落在两次线程唤醒上：驱动完成处理 39 → 120 µs（3.1 倍），用户线程唤醒返回 66 → 162 µs（2.5 倍）。
  2. **不是降频，也不是多做了事**（`data/05_compute/effA_pcpu.txt`）：20 层以上 P 核只有 12–18% 的时间不在最高档，每次调用的 CPU 时间稳定在 112–131 µs。16 层是例外：调用间隔短，P 核忙碌 45%，每次调用 186 µs、99% 在最高档（CPU 几乎不睡）；用户态采样里没有忙等（`data/05_compute/effA_sample.txt`），多出的 CPU 时间在内核或其他进程里。
  3. **占满 CPU 后不再增长**（`data/05_compute/effA_spinner.txt`）：12 个 nice 20 空转进程下，按 p10 推算的主机侧开销在 16 / 20 / 24 / 36 / 48 层为 173 / 183 / 187 / 179 / 196 µs，基本恒定（空转进程会争抢 CPU，中位数不可用；测量时 M6 在播放动态壁纸，有额外噪声）。
- **对使用者的含义**：单次调用的 ANE 时间从约 200 µs 增加到约 400 µs 的过程中，每次调用的主机侧开销会从约 160 µs 逐步增加到约 355 µs；之后不再增加。连续提交、让 CPU 保持忙碌（例如流水线式提交下一次请求）可以避开这部分开销。
- **效应 B（32、34 层的鼓包）是 Core ML 的划分决策**：
  - 编译产物（`anecc` h18g）的结构在 16–40 层完全一致：两个 ANE 各 1 个 kick，TD 流每层固定多 368 字节（`data/05_compute/b6x_hwx.txt`）。
  - 两个 P 核的忙碌时间：30、36 层每次调用约 130 µs，32、34 层约 270 µs，提交事件都在 P 核上（`data/05_compute/b6_pcpu.txt`）。
  - `sample` 显示 32 层时 CPU 在执行 `E5RT::ElementwiseOpCast<_Float16,float>`、`<float,_Float16>`、`vDSP_vthr`（relu）和大量 `memmove`，30、36 层没有（`data/05_compute/b6_sample_top.txt`）。
  - Core ML 缓存里的执行计划：第一轮加载的 28 个模型中，**只有 L32_u、L32、L34_u、L34 的计划带 `main_classic_cpu` 段**，其余都只有 `main_ane`。CPU 段的内容是：`cast`（fp32 → fp16）→ `relu_31` → `cast`，也就是**最后一个 relu 在 CPU 上执行**，计划为 `AneInference → Cast → CpuInference → Cast`。
  - 所以 32、34 层每次调用多出：主机侧两次 1–2 MB 的类型转换加一次 relu（约 90 µs），ANE 任务因输出格式改变多约 20 µs。
  - `anecc` 直接编译完整的 32 层模型（包括最后的 relu）没有问题，所以这不是 ANE 编译器拒绝，而是 Espresso 分段器（加载时日志 "Start / Finished segmenting function"，编译服务 "Ending segment at piece: 31"）做出的划分。为什么只在 32、34 层这样划分，理由在日志中被标为 `<private>`，未查明。
- **W8（只量化权重）的 32 层不属于效应 B**（`data/05_compute/b6_w8_recheck.txt`，两轮）：
  - bondrun 缓存中 W8 L32 的执行计划只有 `main_ane`，换新进程名重新加载也一样；带 CPU 段的只有 FP16 的 L32、L34。
  - W8 的 32 层 806 µs，正好等于直线预测（382 + 13.25 × 32 = 806），16、48 层（413–423 / 1021 µs）也和 FP16 相同。之前看起来"W8 在 32 层也慢"，是拿它和 16 层的效率比，实际只是效应 A。
  - W8A8 的 32 层（426–428 µs，每次调用 3.0 次中断）不慢，是因为每层计算快约一倍、ANE 任务短，仍处在主机开销较低的状态。

### W8A8 与只量化权重（B6 / B7）

- 用 `tools/05_compute/w8a8.py` 生成：
  - W8A8：coremltools `linear_quantize_activations`（4 个样本校准）+ int8 权重；
  - W8：只把权重量化为 int8，激活仍是 fp16。
- 形状同上。原始数据：`data/05_compute/b6_q8_run.txt`。
- L=48 的 W8A8 校准一开始失败：relu 链里激活随深度衰减，scale 变成 0。后来把 `chain.py` 的初始化改成 He（`sqrt(2/(C·k·k))`），只影响数值，不影响耗时。

| 层数 | FP16 | W8（只量化权重） | W8A8 | maderix M4 W8A8 |
|---|---|---|---|---|
| 1 | 201 µs / 2.7 TFLOPS | 199 µs / 2.7 | 206 µs / 2.6 TOPS | 5.9 |
| 4 | 247 µs / 8.7 | 229 µs / 9.4 | 219 µs / 9.8 | 12.4 |
| 8 | 342 µs / 12.6 | 335 µs / 12.8 | 313 µs / 13.7 | 18.6 |
| 16 | 407 µs / 21.1 | 419 µs / 20.5 | 379 µs / 22.7 | 22.4 |
| 32 | 908 µs / 18.9 | 796 µs / 21.6 | 458 µs / **37.5** | 27.4 |
| 48 | 1012 µs / 25.5 | 1011 µs / 25.5 | 726 µs / 35.5 | 36.0（1024 通道、64²） |

L=16→48 的边际吞吐（扣除固定开销）：
- FP16 约 28 TFLOPS；
- W8 约 29 TFLOPS；
- W8A8 约 49 TOPS，约为 FP16 的 1.7 倍。

结论：
1. **W8A8 只有在深链里才明显快于 FP16**：16 层以内几乎没有差别（被固定开销盖住），32 层时快 2 倍。和 maderix 的"W8A8 是整条链的属性"一致。
2. **只量化权重（W8）基本不加速**（L=32 时快 12%，可能是权重字节减半，减轻了读权重的压力），和 maderix "int8 权重 260.4 µs、fp16 260.5 µs，没有差别"的结论一致：MAC 仍按 fp16 计算。
3. 这个形状的 W8A8 绝对值不是峰值，见下面 H10。
4. FP16 在 L=32 时反常地慢（908 µs），而 W8 在线上、W8A8 不慢。原因见 B6b：Core ML 只对 FP16 的 32、34 层把最后一个 relu 放到 CPU 上；和权重总量无关。

### H10：W8A8 的峰值、硬件 Winograd（2026-10-02）

- 工具：`tools/05_compute/w8a8.py`（已改为用 CPU_ONLY 加载做校准，不再触发多余的 ANE 编译）、`tools/common/chain.py`、`tools/05_compute/dilconv.py`、`tools/common/bondrun.m`。全部共享权重，斜率法，每点 400–1000 次调用，两轮。
- 原始数据：`data/05_compute/h10_w8a8_slope.txt`、`data/05_compute/h10_w8a8_k3.txt`、`data/05_compute/h10_dilation.txt`。

| 形状 | 引擎 | FP16 每层斜率 / 吞吐 | W8A8 每层斜率 / 吞吐 | W8A8 ÷ FP16 | W8A8 时 DRAM 读 |
|---|---|---|---|---|---|
| 1×1，512 通道，1×128，L128→384 | 单 | （3.26 µs，20.6 TFLOPS，`bonded_measure.md`） | 2.44 µs，**27.5 TOPS** | 1.34× | 每个 ANE 22–28 GB/s |
| 1×1，512 通道，1×256，L128→384 | 双 | 3.37 µs，**39.8 TFLOPS** | 3.48 µs，**38.6 TOPS** | 0.97× | 每个 ANE 23.5 GB/s |
| 3×3，512 通道，16×16，L32→96 | 单 | 39.0 µs，**31.0 TFLOPS** | 19.4 µs，**62.1 TOPS** | **2.0×** | 20–27 GB/s |
| 3×3 膨胀率 2，同上 | 双（编译器自己切） | 41.4 µs，29.2 TFLOPS（每引擎 14.6） | — | — | |

结论：
1. **1×1 卷积链的 W8A8 受激活带宽限制**：FP16 链的 DRAM 读几乎为 0（激活留在片上），W8A8 链每个 ANE 持续读 22–28 GB/s，而权重是共享的（260 KB）。按带宽 × 每层时间折算，每层约 64 KB（单）/ 160 KB（双），和一层 int8 激活的大小（512 × 128 或 256 字节）相当。推测 W8A8 链中每层的量化 / 反量化让激活经过 DRAM（或 L2 之外），所以双引擎下与 FP16 持平。
2. **计算更密的 3×3 卷积上 W8A8 正好是 FP16 的 2 倍**，对应 int8 双打包（Bryngelson："int8 打包时每核每周期出 8 个输出通道，fp16 出 4 个"）。单引擎 W8A8 有效吞吐 62 TOPS。
3. **硬件 Winograd**：普通 3×3 在单引擎上达到 29–31 TFLOPS，是直接卷积峰值（256 MAC × 16 NE × 2 × 2.58 GHz = 21.1 TFLOPS）的约 1.45 倍；而 Winograd 不适用的膨胀 3×3，每个引擎只有 14.6 TFLOPS（直接峰值的 71%）。编译产物 `__KERN_0` 恰好是 512 × 512 × 9 × 2 字节，权重存的是原始 3×3，变换在硬件里做，和 Bryngelson 反编译的"Winograd 变换矩阵固化在硬件里"一致。F(2×2,3×3) 的乘法减少为 2.25 倍，实测达到其约 66%。
4. 因此"每 NE 每周期 256 次 FP16 乘加"的推断不变；报告里的"峰值"要分开写：直接卷积 20.6 / 39.5 TFLOPS，3×3 有效 31 TFLOPS（单引擎），W8A8 有效 62 TOPS（单引擎，3×3）。
5. B5 里"没有用 Winograd"的结论只对 256 通道、8×16 的形状成立；B4b 中 512 通道、8×32 的 3×3（23.5 TFLOPS）也已超过直接峰值，说明同样启用了 Winograd。
6. int8 路径的累加器位宽：已测，32 位有符号整数（numerics.md H50）。INT8 的 MAC 宽度见下文 H51。

### H51：INT8 MAC 宽度（编译器性能模型，2026-10-03）

- 方法：同一个单层卷积（1×1 / 3×3，通道 32–512，空间 16² / 32² / 64²，共享权重，输入从 DRAM 读）分别编成 FP16、W8（只量化权重）、W8A8 三版（`tools/05_compute/macw.py`，M6 上 `macw/`），逐个 TD 读出形状寄存器（1 / 2 / 3 = Win / Hin / Cin，5 / 6 / 7 = Wout / Hout / Cout，10 = 卷积配置字）和头部 `exe_cycles`，算"每单位 exe_cycles 的乘加次数"（`tools/05_compute/macw_td.py`，结果 `data/05_compute/macw_td.txt`）。再反汇编 `perfmodel::GetNumOutputChannelsPerAccumulator`。
- 编译结果（3×3、512 通道、64²）：

| 精度 | 卷积 TD | 每个 TD | MAC / exe_cycles |
|---|---|---|---|
| FP16 | 6 个 | 输出 96 通道（第一个 32），exe 176 | **10.3 M** |
| W8（只量化权重） | 3 个 | 输出 224 通道（第一个 64），exe 411 | 10.3 M（与 FP16 相同） |
| W8A8 | 8 个 + 2 个量化 TD + 1 个反量化 TD | 半幅 32 行 × 输出 128 通道，exe 58 | **20.8 M（正好 2 倍）** |

  W8A8 的单层被拆成"量化输入（PE，无卷积标志）→ 卷积 → 反量化输出"，总 exe_cycles 不能直接比，只能比卷积 TD。小形状（128 通道以下）W8A8 卷积 TD 的比值低于 2（如 3×3、128 通道、64²：15.9 M），说明那时模型认为瓶颈不在乘加。
- 代码（`ANECompiler`，只读反汇编，`~/anehal/pm/acc.s`）：

  ```
  perfmodel::GetNumOutputChannelsPerAccumulator(PerfHwParams p, bool 是卷积类运算, bool 格式是int8, SmallSourceMode ssm, bool 半工作单元)
    非卷积类                 → p[0x00]
    ssm = 1 / 2 / 3          → p[0x18] / p[0x10] / p[0x08]
    否则 int8 或半工作单元    → p[0x20]
    否则                     → p[0x00]
  ```

  `ZinNEPerfUtils::GetNumOutputChannelsPerAccumulator` 传入"运算模式 == 0"和"张量格式 == 3（int8）"。`ToPerfHwParams` 从 HAL 表拷贝：p[0x00] ← HAL 0x440 = **1**，p[0x08 / 0x10] ← HAL 0x420 = 16 / 8，p[0x18 / 0x20] ← HAL 0x430 = 4 / **2**。H16、H17、H18、H19 的值都一样。

结论：
1. **每个累加器在 FP16 时算 1 个输出通道，在 int8 时同时算 2 个**。乘加阵列的"格子"数不变，int8 把一个格子拆成两路，等价于每 NE 每周期 **512 次 int8 乘加**（FP16 为 256）。这就是 H10 里 3×3 W8A8 正好 2.0 倍的来源，也和 Bryngelson 的"int8 打包每周期 8 个输出通道、fp16 4 个"一致。
2. 只量化权重（W8）在模型里和 FP16 完全相同：int8 权重先解成 fp16 再算，只省读权重的带宽和权重缓冲（每趟能放 224 通道，FP16 只能放 96：每 NE 14 × 512 × 9 × 1 B = 63 KiB ≤ 64 KiB，又一次印证 64 KiB 权重缓冲）。
3. 1×1 实测只有 1.34×（单）/ 0.97×（双），原因是激活带宽（H10 结论 1），不是 MAC 数量。
4. 附带解出 **`exe_cycles` 的单位 ≈ 1 µs**：1×1、512 通道、64² 的 FP16 TD 为 104，按单引擎直接卷积实测 20.6 TFLOPS 折算正好 104 µs（10.3 M MAC / µs ≈ 4096 MAC × 2.5 GHz）。3×3 的 FP16 模型值 58 / 层，实测 39 µs / 层，差的 1.49 倍就是硬件 Winograd（H10 结论 3）——**编译器的性能模型不计 Winograd**。
5. 硬件里 HAL 0x298 = 256、0xc = 16 也被拷进 PerfHwParams（+0x30、+0x28），推测分别是每 NE 的乘加数和 NE 数，但未逐一核对用法。

**第 3 步：实测（2026-10-03）**

- 工具：`tools/05_compute/mac3.py`（共享权重、He 初始化、relu 链，FP16 / W8A8 各 L4、L16）、`tools/common/runall.sh`（每点 300 次，两轮）、`tools/05_compute/mac3_fit.py`（斜率取 p10）。原始数据：`data/05_compute/mac3_run.txt`。
- 形状只选不受 Winograd 和激活带宽干扰的：1×1 且通道 ≥ 1024（每字节激活对应 ≥ 1024 次乘加），膨胀率 2 的 3×3（没有 Winograd）。每 NE 每周期乘加 = 乘加 / 层 ÷ 斜率 ÷（引擎数 × 16 × 2.58 GHz）。

| 形状 | FP16：引擎、每层、每 NE 每周期 | W8A8：引擎、每层、每 NE 每周期 | W8A8 ÷ FP16 |
|---|---|---|---|
| 1×1，2048 通道，16² | 双，77.6 µs，168 | **单，60.8 µs，428** | — |
| 1×1，1024 通道，32² | 双，71.2 µs，183 | 双，40.4 µs，322 | 1.76× |
| 3×3 膨胀 2，512 通道，32² | 双，171.4 µs，171 | 双，91.6 µs，319 | 1.87× |
| 1×1，2048 通道，32² | 双，257.5 µs，202 | 双，212.4 µs，245（切分 1 : 2，按多的一边算为 326） | 1.21× |
| 1×1，512 通道，64² | 双，66.2 µs，197 | L4 异常（3.8–4.4 ms、每次 6 次中断），无法求斜率 | — |

结论：
1. **决定性的一点：1×1、2048 通道、16² 的 W8A8 只用了一个 ANE，跑出每 NE 每周期 428 次乘加（单引擎 35.4 TOPS）**。1×1 没有 Winograd，FP16 单引擎的上限是 256（实测最高 249，即 20.6 TFLOPS），所以 **INT8 的乘加宽度确定大于 256**，与"每累加器同时算 2 个输出通道 = 512"相符，利用率 84%。
2. 两个引擎都参与、且不受切分不均影响的两组，W8A8 是 FP16 的 1.76–1.87 倍，每 NE 每周期 319–322（512 的 62–63%），FP16 为 171–183（256 的 67–71%）；双 ANE 下两者的利用率相近，倍数接近 2。
3. 1×1、2048 通道、32² 的 W8A8 只快 1.21 倍，原因是编译器把它按 1 : 2 切给两个 ANE（bonded 程序 exe_cycles 之和 ANE0 434、ANE1 880；ANE1 读 DRAM 15.6 GB/s、ANE0 7.8 GB/s，都不是带宽限制），是 `defects.md` 已有的"切块不均"问题。
4. 1×1、512 通道、64² 的 W8A8 L4 模型反常地慢（每次 6 次中断），未深究，排除。
5. 因此 **INT8 = 每 NE 每周期 512 次乘加**：编译器参数（第 1、2 步）给出 2 倍，单引擎实测下限 428 > 256。M6 单引擎 INT8 直接卷积峰值 42.3 TOPS，双引擎 84.5 TOPS（3×3 另有 Winograd 加成，H10 实测单引擎 62 TOPS）。

- CSV 的开关：编译选项 `DebugMask`（`setDebugMask` 写 `ZinIrCompilerParameters` +0x118）第 11 位使 `DumpDebugProfilingInfo` 调用 `ZinDebugPrintPerfEstimateParams`（用 `tools/re/strref.c` 定位选项解析代码）。实际设 0x800 / 0x7fffffff 编译都没有产生文件。
- **原因（2026-10-03，`sudo lldb` 调试自己的 anecc 进程，只读断点，脚本 `tools/05_compute/perfcsv_lldb.txt`；静态反汇编 `ANECGetCompilerOptions`，`tools/re/adrstr.c`）**：
  - 编译走 `ZinCompilerCoreClassic::CompileProcedure`，`DumpDebugProfilingInfo` 每个程序（nonbonded / bonded）调用一次；它检查的参数字（+0x110 起）全为 0，`setDebugMask` 从未被调用。
  - `ANECGetCompilerOptions` 解析顶层 `DebugMask`（+0x84c–0x898）前有一道静态开关：`os_variant_has_internal_content("com.apple.ane")`（+0x192c 的字符串参数；ANECompiler 导入 `_os_variant_has_internal_content`），结果为真才读取。**零售版系统上为假，`DebugMask` 被忽略，性能 CSV 不可能产生**。
  - 另一处解析（`ANECGetTargetOptions` +0x16a4）读 `flags["all"]` 子字典（键名用 `tools/re/adrstr.c` 解出），但实测放入 `all` / 架构名子字典的选项（以 `NeFrequency` 验证）都不生效；顶层 `NeFrequency` 生效（1308 MHz 时 exe_cycles 176 → 338），说明顶层选项解析正常，只是调试开关被内部版检查挡住。
  - `tools/common/anecc.m` 增加了 `子字典.键=值` 与 `O:键=值`（放入 options 字典）两种写法，供以后试验。
- **拿到 CSV（经用户同意）**：`tools/common/anevariant.c` 编成动态库，用 `DYLD_INSERT_LIBRARIES` 只在我们自己的 anecc 进程里把 `os_variant_has_internal_content("com.apple.ane")` 视为真（其余参数照常调用原函数；不改系统文件或设置，编出的 HWX 只读不执行）。顶层 `DebugMask=0x800` 后，输出目录多出 `model.hwx.h18g_perf_all.csv`，每行一个 TD，列：`is_chained, NumWU, mac_cycles_per_WU, post_cycles_per_WU, ne_cycle_single_buffering, ne_cycle_double_buffering, pe_cycle, l2_bcast, lw_writeback, kdma, rdma, wdma, core_cycle_count, l2_cycle_count, power(W), estimated_time(ms)`。批量工具 `tools/05_compute/perfcsv.py`（与 TD 形状、OCG 对齐），数据 `data/05_compute/perfcsv/`（`ocgm_table.txt` 为 56 个单层卷积模型的汇总）。
- **CSV 揭示的性能模型**（编译器视角，未全部经实测验证）：
  1. **两个时钟**：估计耗时 = 核心周期 ÷ 2.508 GHz（NE，编译器表最高档）；纯 PE 的 TD 估计耗时 = PE 周期 ÷ **1.812 GHz**（= `GetMapNEToL2Frequencies` 中 NE 2508 对应的 L2 频率）。**编译器把 PE 放在 L2 时钟域**，与实测"PE 时钟独立于 NE"一致。
  2. **工作单元（WU）**：FP16 卷积每个 NE 每个 WU 处理 128 或 256 个输出像素（如 64² → NumWU 32 × 128 像素）；INT8 为 256 或 512 个。`mac_cycles_per_WU` ≈ 像素 × Cin × kH × kW × 每 NE 输出通道 ÷ 每周期乘加 + 1；`post_cycles_per_WU` 为后处理（184–1616，随输出通道数增长）；单 / 双缓冲周期之差约等于 NumWU × post。
  3. **每 NE 每周期乘加**：FP16 一般 **256**；输入通道 64 时为 **512**（1×1 / 1×3 / 3×1 / 2×2 / 3×3 均如此，即小输入通道模式，对应 HAL 0x420 / 0x430 的 SmallSourceMode 档位）；INT8 为 **512** 或 **1024**（每 WU 256 像素时 512，512 像素时 1024；如 1×1、Cin 256–512 以及 3×3、Cin 256 为 1024，3×3 / 5×5 / 7×7、Cin 512 为 512）。实测：FP16 单引擎 247.5（与 256 一致）；INT8 1×1、2048 通道单引擎 428（H51），**1024 档与 FP16 小输入通道的 512 档都未经实测验证**。
  3b. **高档位的来源与实测核对（2026-10-03）**：在链式模型（`mac3.py val ...`，`tools/05_compute/perfcsv.py`）里，每 NE 每周期乘加 ≈ 2 × 每 WU 像素数，FP16 与 INT8 相同（FP16：128 像素 → 256、256 像素 → 512；INT8：256 → 512、512 → 1024）；"Cin 64 → 512"只是单层 32² 时编译器恰好选了 256 像素的 WU，链式 1×1、64 通道、128² 为 254。档位取决于编译器选的 WU 大小，空间尺寸越大越可能选到大 WU。
     - 实测（`data/05_compute/val_run.txt`，墙钟斜率 L4 → L16，两轮，全部被切给两个 ANE）：FP16 2×2、256、64²（模型 512）实测 189；INT8 2×2、256、64²（模型 1024）311；INT8 3×3、256、64²（模型 1024）523（可能含 Winograd）；FP16 1×1、64、128²（模型 254）93。都远低于模型，但受双 ANE 切分与激活 DMA 干扰（FP16 2×2 每层读约 2 MB，折合约 30 GB/s，接近 Tile DMA 上限），不能据此否定。
     - 已有的单引擎、计算受限的干净实测点全部落在**基础档**：FP16 1×1、512、1×128 模型 256 / 实测 247.5；INT8 1×1、2048、16² 模型 512 / 实测 428。
     - 结论：**基础档（FP16 256、INT8 512）已被实测确认；高档（FP16 512、INT8 1024）目前没有实测支持**，需用 kdebug 读单个引擎的任务时长、在大 WU 且不受 DMA 限制的形状上再测。
     - **kdebug 复测（`tools/05_compute/hi_ktrace.sh`、`tools/05_compute/hi_fit.py`，ANE 自身忙碌时间，L4 → L12；数据 `data/05_compute/hi_kt/`）**：FP16 2×2、256、32×64 → 257；FP16 2×2、128、64² → 214；FP16 1×1、256、32×64 → 194；INT8 2×2、256、32×64 → 413；INT8 2×2、128、64² → 323（每 NE 每周期，2.58 GHz）。这些层运行时都执行 **bonded 程序**，且都**按行切分**（每个 ANE 分到一半行，如 32×64 → 16×64），WU 随之减半，**bonded 程序的模型档就是基础档**（CSV 第二组行：FP16 256、INT8 512），实测与之吻合（257 / 256；413 / 512 = 81%）。单 ANE 程序的高档根本没有被执行。
     - 编译器对 DMA 偏乐观：单 ANE 程序里 FP16 1×1、512、64² 的 TD 估计 52.3 µs（512 档、计算受限），但它同时要读写各 2 MB 激活，折合每 ANE 约 80 GB/s，而实测 Tile DMA 只有 35–40 GB/s；大 WU 的形状多半张量大、激活走 DRAM，硬件上会被 DMA 卡住。
     - 能让 Core ML 用单 ANE 程序的形状（不被切分）在 1–6 层都找不到：这些形状每块 > 128 像素，切分无拷贝开销，编译器总选切分；按通道 / 按块分给两个 ANE 的情况，TD 形状本身就是小 WU。**正常使用 Core ML 时，高档基本不会被执行**。
     - 试图让单 ANE 程序执行：同一模型两个进程并发（`tools/05_compute/hi2_ktrace.sh`、`tools/05_compute/hi2_fit.py`，数据 `data/05_compute/hi2_kt/`）。结果两边任务 73–100% 同时开始，单个任务时长与单独运行的 bonded 程序相同（如 FP16 2×2、256、32×64、L12：并发 363 µs，单独 349 µs）——内核让两个进程**轮流使用两个 ANE、仍执行 bonded 程序**，没有改派单 ANE 程序（`hi2_fit.py` 中"单 ANE 每层"一栏因此不成立，应减半，与上一轮一致）。
     - **最终结论**：编译器性能模型里的高档（FP16 512、INT8 1024 每 NE 每周期）只出现在单 ANE 程序的大 WU 形状上；在 M6 上通过 Core ML 实际执行的程序（bonded、按行切分）都落在基础档，实测与模型对实际程序的预测一致（FP16 257 / 256，INT8 413 / 512）。高档在硬件上是否真能达到，**用 Core ML 无法验证**（需要直接执行单 ANE 程序，按约定不做）。
  4. **PE**：纯 PE 的 TD `pe_cycle = l2_cycle_count`；256 × 32² 每 TD 4096 周期（每周期 64 个元素），128 × 64² 每 TD 16384 周期（每周期 32 个）；把两个单输入运算合并的 TD 与单个运算周期相同。对照实测（5 点回归）：32² 时模型每 TD 116 G 元素 / s，实测合并任务约 55 G、折合单个运算约 110 G；双输入加法实测约 29 G，远低于模型。PE 每周期宽度仍无法从模型与实测唯一确定（64 或 32，取决于张量宽度与合并任务是否算两遍）。


**TD 中的 NE 配置**（v24 设置函数反汇编；对象 0x274 = 任务信息 = 寄存器 0xf，于是）：

- 寄存器 **0x10 = NE 配置**：`OcgSize`（log2）[2:0]、`HalfWUMode` [6]；
- 寄存器 0x11：`PatchWidth` [3:0]、`PatchHeight` [8:4]（只在含 PE 量化的 W8A8 模型里出现，属于 PE）；
- `NEBinaryPoint` 在对象 0x504 [13:8]。

**OCG 扫描**（`tools/05_compute/ocg.py`：单层卷积，核 1×1 / 1×3 / 3×1 / 2×2 / 3×3 / 5×5 / 7×7 × Cin 16–512 × FP16 / W8A8，32²；结果 `data/05_compute/ocg_table.txt`）。OCG = **每个 NE 每轮算几个输出通道**；一个 TD 可以跑多轮，所以和 TD 的 Cout 不同（如 3×3、256 通道：TD 的 Cout = 224，OCG = 2）。TD 只写与上一个 TD 不同的寄存器，解析时沿流累积状态。

| FP16 的 OCG | Cin 16 | 64 | 256 | 512 |
|---|---|---|---|---|
| 1×1、3×1、2×2 | 16 | 16 | 16 | 16 |
| 5×5 | 16 | 16 | 4 | 2 |
| 7×7 | 16 | （异常：两个 TD 分别为 1 / 16） | 2 | 1 |
| 3×3、1×3（Winograd，任务信息 bit 27 = 1） | 1 | 1 | 2 | 2 |

结论：

1. **FP16 时每个 NE 每轮最多算 16 个输出通道**；再往下由权重缓冲决定：OCG = min(16, 不超过 64 KiB ÷ (Cin × kH × kW × 2 B) 的最大 2 的幂)。2×2、512 通道正好 16 × 512 × 4 × 2 B = 64 KiB。这是"每 NE 64 KiB 权重缓冲"的又一条独立证据。
2. INT8（W8A8）的 OCG 同样受 64 KiB 限制，按每个权重 1 B 计（7×7、256 通道 = 4；512 通道 = 2；5×5、512 通道 = 4）；公式给出 ≥ 8 时该字段不写（为 0），含义未定。
3. Winograd 卷积的 OCG 很小（1–2），不受权重缓冲限制（3×3、256 通道变换后的权重每 NE 每轮只有 2 × 256 × 16 × 2 B = 16 KiB），推测受累加器容量限制（每个输出要在变换域累加 4×4 块）。
4. 推测：每 NE 每周期 256 次 FP16 乘加 = 16 个输出通道 × 16（输入通道或像素），与 OCG 上限 16、NE 工作单元 16 一致；未证实是哪一种。
5. 文献的"累加器文件深 8"（Bryngelson）在 M6 的 OCG 上看不到直接对应（OCG 可达 16），可能是单位不同，未定。
6. **与 B2 的台阶对上**：OCG 上限 16 × 16 个 NE = 每轮 256 个输出通道。1×1 卷积的 Cout 从 256 增到 272 时要多跑一轮（输入要重读一遍），正是 B2 实测里唯一的明显台阶（+32%）。

**第 2 步：PE 吞吐实测**（`tools/05_compute/pe.py`：`x ← x + y` / `x × y` / 加乘交替，L16 → L64 斜率，`runall.sh` 每点 300 次、两轮；原始数据 `data/05_compute/pe_run.txt`）

- 编译：每层正好一个 PE 任务（标志字 0x1），除第一层外都不带 DMA 地址包；运行时两个 ANE 读写 DRAM 都只有底噪 0.5 GB/s → 数据全在 L2。所有模型都被切给两个 ANE；64 通道 L16 的模型被放到了 CPU（0 中断），已排除。

| 形状（每个 ANE 处理一半） | 每层 | 每 ANE 元素 / 周期（按 2.58 GHz） | 折合 L2 读写（每元素 6 B） |
|---|---|---|---|
| 256 × 32²，加 / 乘 / 交替 | 6.95–7.23 µs | 7.0–7.3 | 109–113 GB/s |

结论（初步）：
1. 加法和乘法一样快，交替也一样 → 不是运算本身的限制。
2. 每个 ANE 每周期只处理 7–14 个元素，远低于 HAL 的"PE 工作单元 64"；张量越小反而越快（64 × 32² 最快），说明有与数据量相关、但不是 DRAM 的限制（L2 读写、或 L2 / PE 时钟域低于 2.58 GHz）。编译器对 256 × 32² 每层的估计是 4（约 4 µs，单引擎），实测双引擎每层 7 µs，模型偏乐观。
3. **因此 PE 的"宽度"测不出确定值**：总耗时里混着双 ANE 切分和 L2 读写；要分开，需要 kdebug 读单个引擎的任务时长，并做单输入运算（如 `x × 常数`）对照 L2 读写字节数。列入未完成。

| 单输入（abs、×(−1)、relu 两两合并为一个任务），256 × 48² | 5.44 µs / 任务 |

- （此条已被下面的 5 点回归修正）**双输入时每层的耗时几乎不随元素数变化**：两点拟合为"每层约 4.3 µs 固定 + 每引擎约 330 G 元素 / s（≈ 每周期 130 个元素）"。只有两个尺寸，吞吐的误差很大，只能说明 PE 每周期处理的元素远多于前面按调用总耗时估的 7–14 个（那是被固定开销拖低的），量级与 HAL"PE 工作单元 64"相当或更高。
- 单输入和双输入每层耗时接近 → 也不是 L2 读写带宽的限制。
- 之前按调用总耗时求的斜率（256 × 32² 每层 7 µs）比 ANE 忙碌时间（4.68 µs）大，多出的是"任务越长、主机唤醒越慢"（memory.md / scheduling.md D1c 的已知现象）。
- 每层约 4 µs 的固定开销来源未查明（编译器对该层的估计也是 4，说明性能模型里同样有大块固定成本；可能是层间依赖导致的流水线排空，或双 ANE 每层同步）。**PE 宽度仍未定**；要定，需要更多尺寸（让元素数主导）并设法让模型只跑单个 ANE。

**第 2 步再补测：5 个尺寸回归**（256 通道，H = W = 32 / 40 / 48 / 56 / 64，L32 → L96；每个 ANE 每层正好一个任务，单输入运算两层合一个任务；`tools/05_compute/pe_kt.py`，结果 `data/05_compute/pe_kt_fit.txt`）

| 每引擎元素数 | 单输入：每任务（两个运算） | 双输入 `x + y`：每层 |
|---|---|---|
| 131 072（32²） | 2.38 µs | 4.55 µs |
| 204 800（40²） | 3.88 µs | 4.39 µs |
| 294 912（48²） | 5.22 µs | 5.19 µs |
| 401 408（56²） | 6.86 µs | 11.94 µs |
| 524 288（64²） | 8.98 µs | 18.49 µs |

1. **单输入 PE 是一条干净的直线**（最大残差 0.09 µs）：每任务固定约 0.34 µs，每个 ANE 约 **61 G 元素 / s ≈ 每周期 23.5 个元素**（按 2.58 GHz；±2σ 约 ±5%）。每个元素读 2 B、写 2 B，折合 L2 读写约 243 GB/s / 引擎（≈ 94 B / 周期）。
2. **双输入 PE 不是直线**：32²–48² 每层停在 4.4–5.2 µs，56²、64² 跳到 11.9、18.5 µs（这一段的边际只有约 6.7 个元素 / 周期）。双输入的每元素成本远高于单输入，与 HAL 0x5f6"双输入 PE 只有一个 DMA 引擎"一致：两路输入由同一个引擎先后从 L2 取，且到 56² 起（每引擎三个张量各约 0.75–1 MiB，接近 L2 容量）还有额外的限制。上一节"每层约 4.3 µs 固定开销"只适用于双输入，不是 PE 的普遍特性，予以更正。
3. **PE 宽度**（已由下一节"PE 的时钟"更新）：实测单输入每周期 23.5 个元素（若按 2.58 GHz）。HAL 的"PE 工作单元 64"与之不直接对应；性能模型显示 L2 / PE 有独立时钟域（`run_cycle_in_l2_freq_domain`），若该时钟低于 2.58 GHz，每个时钟处理的元素会更多（例如约 0.95 GHz 时正好 64）。时钟没有测到，**宽度只能给出"每秒 61 G 元素 / 引擎"这个绝对值**。

**PE 的时钟（2026-10-03）**

- **编译器的 NE → L2 频率映射**（`ZinIrSocVariantParams::GetMapNEToL2Frequencies` 读数据块 +0x58，libc++ `std::map<double,double>`；`tools/re/socfreq_map.c`，数据 `data/09_clock/socfreq_ne2l2.txt`，含 H16g / H17s / H18 / H19 / Soc2026BaseLine）：M6 用的 Soc2026BaseLine 为 32 档一一对应，L2 ≈ NE × 0.85（804 → 684 MHz）… × 0.72（2508 → 1812 MHz）。之前以为的"L2 五档 534–1308 MHz"是 +0x40 的 DMA 表。
- **实验 1：单独升频**（`tools/09_clock/pefreq_ktrace.sh` / `pefreq_ktrace2.sh`，sudo；卷积与 PE 模型交替从空闲开始，`tools/09_clock/pefreq_fit.py`；数据 `data/09_clock/pefreq_kt/`、`data/09_clock/pefreq_kt2/`）：卷积任务 3810 → 1267.5 µs（3.01 倍 = NE 852 → 2580 MHz）；PE（`x` 单输入链，256 × 64²）L96 1193 → 466.0 µs，L32 438.5 → 178.8 µs，**L96 − L32（64 个 PE 运算、不含固定部分）754.5 → 287.2 µs，2.63 倍**。程序里不属于 PE 的部分（开头读、结尾写 DRAM）从约 61 µs 降到约 35 µs，按第三种比例变化。
- **实验 2：三个进程交错**（`tools/09_clock/pefreq_ktrace3.sh`、`tools/09_clock/pefreq_fit3.py`；数据 `data/09_clock/pefreq_kt3/`，第一版 `pefreq_kt3_v1/` 因启动顺序不对作废）：PE L96 = 1193 µs、L32 = 436 µs（PE 的最低档值）与 1257–1315 µs 的卷积任务（NE 已满载）交替出现；另一段里卷积处于低档（约 3000 µs）时 PE 却已不在最低档。
- 结论：
  1. **PE 不在 NE 时钟域**：同一时刻 NE 已满载而 PE 仍在最低档，反之亦然——PE 的时钟是**独立调度**的，并不像编译器映射表那样与 NE 同步（映射表只是性能模型的假设）。与性能模型的 `run_cycle_in_l2_freq_domain` 一致，判断 PE 在 L2 时钟域。
  2. PE 时钟最低档到满载为 2.63 倍。对照候选表：NE 表（需从 982 MHz 起，不在表上，且已被实验 2 排除）、DMA 表（最大比值 2.45，排除）、编译器 L2 值域（起点 684 / 696 / 720 MHz → 满载 1.80 / 1.83 / 1.89 GHz）。**满载 L2 / PE 时钟约 1.8–1.9 GHz**，无法更精确（没有该时钟域的档位表或读数）。
  3. 由此 **PE 宽度 ≈ 61 G 元素 / s ÷ 1.8–1.9 GHz ≈ 每个 L2 周期 32 个 FP16 元素**（即每周期读 64 B、写 64 B），与 HAL"PE 工作单元 64"（按字节）吻合。前面"按 2.58 GHz 每周期 23.5 个"作废。
  4. 局限：L2 时钟的绝对值是借编译器 L2 值域推的，不是直接读数；"32 个 / 周期"依赖这一点。
- **找独立的 L2 / PE 档位表（未找到）**：
  - 编译器：频率相关函数只有 `GetValidNEFrequencies`（+0x10，32 档）、`GetValidDRAMFrequencies`（+0x28）、`GetValidDMAFrequencies`（+0x40，5 档）、`GetMapNEToL2Frequencies`（+0x58，32 项）、`GetMax/Mid/MinFrequenciesAndLevels`（只返回 NE 频率、DRAM 档号、DMA 档号）、`GetClosestValidFrequency`。L2 频率在编译器里完全由 NE 经映射表推出，没有自己的档位。
  - 设备树 pmgr：`voltage-states8` / `29` 为两个 ANE 的 NE 时钟（明文 Hz）；`voltage-states0`（7 档）、`2`（8 档）、`11`（7 档）每项为 (1, mV)，频率被隐藏，其中可能有 PE 所在的时钟域。
  - kernelcache：ANE 驱动有可单独开关、单独动态门控的 **`ANE_SYS`** 时钟（另有 `ANE_DPE_SYS`、`SNE1_ANECLKGEN_TOP`），PE / L2 很可能在该域。
  - **PMGR 驱动**（`com.apple.driver.AppleT8152PMGR`，从 kernelcache fileset 拆出，`tools/re/kcdis.py` 反汇编，字符串引用扫描）：初始化序列无条件调用"构建 CLPC DVFM 字典"和"打印"两个函数。字典结构：`ACC Complex %u` 的 `DVFMStates`（CPU 簇档位：`StateID`、`Frequency`、`Voltage`、`fANE0` / `fANE1` / `fANE2`、`MaxDVMRWeight`），以及按 ANE 编号循环的 `ANE%uFrequencies`（`IDS`）。`fANE0–2` 挂在 **CPU 档位**上、上限 `kFANEIDMax` = 3，应为各 ANE 实例对应的档位号，不是一个 ANE 的三个时钟域。ANE 频率表 `_anePerfStateFrequenciesMHz` 即 NE 的 32 档（设备树 `voltage-states8/29`）。驱动里没有 `ANE_SYS` / L2 的档位表，只做开关与门控；打印函数受调试开关控制、输出到内核串口，系统日志里没有。字典存在驱动内部（对象 +0xbb0），未发布到 IORegistry。
  - **固件与 CLPC**（只读）：
    - ANE 固件只有 `pstate=%d`（接收档位号）和 `System Clock : %zu Hz`（固件处理器计时时钟），没有频率表；
    - PMP 固件（`t8152pmp.bin`）按设备树 `%s-dvfs-state-voltages` 管理 DCS / SOC / DISP 三个调压域；0x38d78 有 DRAM 频率表（732 … 5328 MHz，与编译器一致），没有 SOC 或 ANE 的频率表；
    - **`AppleT8152CLPC`**（kernelcache）：`Fabric DVFM`（`fabric_dvfm_table.cpp`、`fabric_dvf_manager`），常量区 0x753ed8 正是编译器的"DMA 表" 534 / 712 / 1068 / 1150 / 1308 MHz，紧邻 DRAM 速率表（1464 … 10656 MT/s）→ **编译器的 DMA 表 = SoC 互连（fabric）的 5 档**，对应 SOC 调压域的 5 个电压档。CLPC 还管理 **`ANE Shared Cluster` / `aneshared` / `SharedANEClusterMask`**：两个 ANE 共用的部分作为独立的簇调频，与实测"PE 时钟独立于 NE"一致，PE / L2 很可能在此簇。各簇的 DVFM 表由 PMGR 在运行时提供（`dvfm table provided by PMGR for %s cluster %u`）。`fANE0–2`（上限 3）可能对应 ANE0、ANE1、共享簇，未证实。
    - 设备树电压表的频率字段编码为 65536 × 10⁹ ÷ f（E 核 `voltage-states1`：67423 → 972 MHz，22291 → 2940 MHz）；`voltage-states0` / `2` / `11` 的频率字段为 1，确实没有给频率。
    - 在 PMGR、CLPC 的常量区按 MHz / kHz / Hz 扫描单调数组，没有找到 NE 表以外的 ANE 频率表；共享簇的频率应由 PMGR 在运行时按时钟树寄存器算出，静态二进制里没有。
  - **设备树性能域与电压表的对应**（`perf-domains`，每项 28 字节，首字节为 `voltage-states` 编号；`dvfs-domain` 列出 PMP 的调压域 DCS 9 档、SOC 5 档、DISP 7 档）：SOC → `voltage-states0`，ECPU → 1，DCS → 2，PCPU → 5，ANE → 8，ANE1 → 29，DISP → 11。**ANE 只有两个性能域（两个 ANE 的 NE 时钟）**，共享簇 / L2 / PE 没有自己的电压表；`voltage-states0` 是 SOC、`11` 是显示，都不是 ANE。
  - **PE 负载把 SOC 域推到最高档**（`iorlist SOC_V 3` / `iorlist Floor 3`，各负载跑约 6 s、中段采样 3 s）：

    | | 空闲 | PE 链（单输入 / 双输入，256 × 64²） | 卷积链（1×1、512、L384） |
    |---|---|---|---|
    | SOC 实际档位 | 多在 VMAX | **VOVD2 93% / 99%** | VMAX 97% |
    | `SOC Floor / ANE0-AF-BW`、`ANE1-AF-BW` | VMIN | **VOVD2 89%** | VNOM 97–98% |
    | `SOC Floor / ANE0-LINK0/1-AF-B` | VMIN | VMIN | VMIN |
    | `PMC SOC Floor / PMP`（汇总） | VMIN | VOVD2 89% | VNOM 98% |

    ANE 自身的 SOC 下限投票（`SOC Floor / ANE0`、`ANE1`）始终为 0；推高 SOC 的是 **ANE 与 SoC 互连（AF）接口的带宽投票**。PE 链读写 DRAM 只有约 0.5 GB/s，说明 PE 链的数据流确实经过 ANE–AF 接口（L2 / PE 的数据通路与 SoC 互连相连，或 L2 本身在 AF 一侧），而卷积链不会产生这种流量。
  - ~~推论：PE 的吞吐受 SOC 域（SoC 互连）档位影响~~ → **已被下面的对齐实验否定**。
  - **PE 速度与 SOC 档位按时间对齐**（`tools/common/socsamp.c`：每约 25 ms 读一次 SOC 实际档位、PMP 汇总下限、ANE0-AF-BW 投票，mach 时基；`tools/09_clock/socpe_ktrace.sh`（sudo）同时记 kdebug；`tools/09_clock/socpe_fit.py`；数据 `data/09_clock/socpe_kt/`）。轮次：A 只跑 PE（`x` 单输入，256 × 64²，L96）冷启动 ×4；B 只跑卷积 ×3；C GPU 读内存先跑 1.5 s 再冷启动 PE ×3：
    - A：PE 在 1193 µs 慢台阶上停约 **0.4–0.5 s**（同条件下 NE 约 50 ms 升满），期间 SOC 为 VMAX、PMP 下限 VMIN；随后在 826 / 607 / 701 / 927 / 1012 / 650 / 496 µs 之间摆动，最后稳定在 466 µs；SOC 在 PE 提速**之后**才升到 VOVD2。
    - C：SOC 与 PMP 下限从头到尾都是 VOVD2，PE 仍先停在 1184 µs 慢台阶 0.3–0.7 s（与 A 只差 0.7%）；提速后**又被压回 1184 µs，反复多次**，整轮未稳定在快档。
    - B：卷积按 NE 档位在约 50 ms 内升满（与 power.md §6.5 一致）。
  - 结论：
    1. **SOC 档位不决定 PE 速度**；"PE 负载把 SOC 推到 VOVD2"是 PE 提速后 ANE–AF 流量增大引起的结果。
    2. **PE 时钟是单独调度的时钟域**：调度反应慢（约 0.5 s 才开始升）、提速过程中来回摆动，并且**GPU 同时工作时会被反复压回慢档**。与 CLPC 中"共享 ANE 簇"单独调度、`fabric_power_limiter` / `FabricComputePowerRatio` 一致。该域没有电压表、频率表或 IOReport 档位统计，**绝对频率读不到**；只知道慢档到满载为 2.63 倍、满载 PE 每 ANE 约 61 G 元素 / s。
    3. 实际影响：ANE 与 GPU 同时工作时，PE 类运算（逐元素、激活等）可能长期处于慢档（最多慢约 2.6 倍）；短于约 0.5 s 的推理，PE 部分基本跑在慢档。
  - 结论：PE 所在时钟域的 DVFS 不经过 CLPC 的 ANE 档位表，应由 ANE 固件或 PMP 自主管理；其频率可能在设备树被隐去频率的 `voltage-states0` / `2` / `11` 中。内核里的完整设备树也许有真实值，但读取需要内核调试或改启动参数打开驱动调试输出（需改系统安全设置，不做）。
  - 在 kernelcache、PMP 固件、ANE 固件中按 u16 / u32（MHz / kHz / Hz）、f64、各种结构步长搜索 NE 频率序列，连 NE 表都没有找到：这些表由运行时从设备树读入，二进制里没有副本。

**第 3 步：L2 bank 与输入缓冲（只编译）**

- **L2 bank**（`tools/07_memory/l2bank.py`，3×3 卷积链，C = 64 / 128，H = 16，W = 8–136；默认与 `DisableL2BankConflictOpt=true` 各编一次；结果 `data/07_memory/l2bank_table.txt`）：
  - 关掉优化时，L2 张量步长寄存器（0x1044 / 0x1053，以及 0x1046 / 0x1055，值以字节计、低 4 位为标志）都是 **1024 B 的整数倍**；
  - 默认编译在这些步长上再加 **0x200 或 0x300（512 / 768 B）**，随宽度交替；
  - 即 bank 的循环周期是 **1024 B = 64 个 bank × 16 B**：步长为 1024 的整数倍时，每个通道平面都从同一个 bank 开始；补 512 / 768 B 把起点错开 32 / 48 个 bank。与 HAL（0x1e8 = 64、0x1e0 = 16）、maderix / Bryngelson 的"64 bank、16 B 交错"一致，现在有 M6 编译产物的证据。
  - 两种编译的 exe_cycles 完全相同（性能模型在这些形状上没有给冲突计惩罚）。实际耗时无法对比：运行时由 Core ML 编译，传不进这个选项；按约定不直接加载自己编译的 HWX。
- **输入行缓冲**：TD 中没有对应字段；这些形状的 TileHeight（寄存器 0xd）始终等于整个 H，说明 L2 里不需要切行，NE 内部的行缓冲容量从编译产物里看不出来。间接线索只有：HAL 0x68 = 32（`GetMaxLogicalKernelHeightForLargeKernelMode`，大核模式的逻辑核高上限 32）；核宽 9–15 被编译器改写为步长 2（B4c），说明硬件原生核宽有上限。**结论：测不出。**
- 顺带：HAL 0x5f6 = 1，读者是 `ZinMirInterleaveInitializer::IsDualInputsPEWithSingleDMAEngine`（H16–H19 都是 1）——"双输入 PE 运算只有一个 DMA 引擎"，与 memory.md C3b 实测的"两路输入共用一份带宽"吻合。

### B4c：长条形卷积核效率低的原因（2026-10-03）

- 工具：`tools/common/chain.py`（k{kH}x{kW} 命名）、`tools/05_compute/kshape_fit.py`（斜率、有效吞吐、相对直接卷积峰值的效率、每行 / 每像素耗时）、`tools/lib/td_widths.py`、`anecc`。256 通道、共享权重（每层权重 ≤ 1.2 MB，不受读权重带宽限制）。原始数据：`data/05_compute/kshape_run.txt`（32×32 等，L4 / L12）、`data/05_compute/kshape2_run.txt`（8×64、宽度扫描，L4 / L20）、`data/05_compute/kshape_td.txt`（编译产物）。
- 注意：很多形状在层数变化时会在单 / 双引擎之间切换（例如 8×64 的 1×9 在 4 层单引擎、20 层双引擎），这些点的斜率无意义；下面 1–7 只用单 / 双引擎一致的点。第 8 点用不切换的形状和固件时间戳重测了一轮，并修正了第 3、5 点的解释。
- **1. 核宽 ≥ 16：ANE 编译器拒绝，整个模型退回 CPU**。`ANECCompile` 对 1×16、1×17 返回 1（h18g 和 M4 的 h16g 都一样）；经 Core ML 加载时不报错，ANE0、ANE1 中断都为 0，每层 250–530 µs（是 1×15 的 4–7 倍）。核高没有这个限制：17×1 编译正常（每层 6 个 TD），单引擎效率 82%。与论文"fp16 卷积核宽度上限 15"一致。
- **2. 大核被拆成多个 TD**（每层卷积 TD 数，16×32、256 通道，用 4 / 8 层的差求得）：

| 核 | 1×1、1×3、1×5 | 9×1 | 3×3 | 1×9 | 5×5 | 1×15 | 17×1 |
|---|---|---|---|---|---|---|---|
| 每层 TD 数 | 1 | 2 | 2 | 3 | 4 | 6 | 6 |
| 每层 TD 流字节 | 368 | 736 | 720 | 1072 | 1472 | 2112 | 2112 |

    - 16×32 的 1×9、1×10、1×11、1×15：**按行切分**，每个 ANE 8 行、全部 256 个输出通道，每个 ANE 都读一份完整权重。两个 ANE 共享约 150 GB/s，所以每层耗时是单 ANE 的 2 倍：1×9 为 33.0 µs，预测 2 × 2.53 MB ÷ 150 GB/s = 33.7 µs。**第二个 ANE 完全没有带来加速**。
    - 16×32 的 1×12–1×14：**按输出通道切分**，每个 ANE 128 个通道、16 行，各读一半权重。每层 24.9 µs，预测 3.37 MB ÷ 150 GB/s = 22.5 µs；效率 76% 而不是 43%。
    - 32×32 全部按行切分（每个 ANE 16 行）：两份权重 ÷ 150 GB/s 与实测一致（1×9 预测 33.7、实测 33.1；1×15 预测 55.9、实测 55.6）。行数多了，所以计算量和读权重量大致平衡，效率 86–89%。
    - 对受读权重限制的层，按输出通道切分明显更好；编译器的选择在 16×32 上让一半的核慢了 1 倍（defects.md B9）。
  - 单 ANE 4×32 的 1×9 每层只有 1 个 TD（全部 256 个输出通道，`Hin = 4`），8×32 是 3 个（64 + 96 + 96）。"每层 TD 数 = ⌈每 NE 权重 ÷ 64 KiB⌉"（第 7 点）只在部分形状下成立，编译器也可以在一个 TD 内连续读权重。两种情况下的耗时都由读权重决定。
- **结论**：长条形核本身不慢，慢的是**核宽 > 8 时的改写**：权重量变为约 2 × (核宽 + 1)，权重超出每 NE 64 KiB 的缓冲，每层都要以约 150 GB/s 重新读入，于是耗时由权重量决定，与计算量无关。像素少（4×32 时 42%）或双 ANE 按行切分（两个 ANE 共享带宽、各读一份）时效率减半，像素多时（8×32 单 ANE、32×32 双 ANE）为 85–89%。原生核（核宽 ≤ 8、竖向核到 15）在单 ANE 下为 90–96%。之前看到的"1×9 效率 18–60%"是窄宽度按行计时（第 3 点）、读权重带宽，以及单 / 双 ANE 切换造成的斜率错误叠加的结果。核宽 ≥ 16 完全无法在 ANE 上运行。


## sparse：权重稀疏与激活稀疏（2026-10-04，M6 / M4）

工具 `tools/05_compute/sparse_gen.py`（coremltools 9.0 `prune_weights` / `palettize_weights(joint_compression=True)`）、`sparse.sh`、`sparse_fit.py`、`sparse_err.py`；数据 `data/05_compute/sparse/sparse.txt`（汇总）及 `m6_v1`、`m6_v2`、`m4_v1`、`m4_v2`。

**问题**：① 剪枝后的权重是否按压缩格式读入（补 wfmt）；② 硬件是否跳过零权重的乘加；③ 是否跳过零输入（用来解释 14.4 节全 0 输入下 55.6 TFLOPS、13.3 节卷积输入全 0 功耗 +7.5%）。

**模型**：同一份 FP16 基准权重，层间 ReLU、偏置 0。
- m2048：1×1、2048 通道、32 像素、各层权重不同（读权重受限，同 wfmt），16 / 32 层；
- c1x1：1×1、512 通道、1×128、各层共享（权重留在片上，计算受限），32 / 128 层（第一轮 16 / 32）；
- c3x3：3×3、512 通道、16×16、各层共享，16 / 32 层。
- 权重版本：稠密；非结构化剪 50 / 75 / 90%；n:m = 2:4、1:4（每 4 个留 1 个）；剪 50% + 4 位调色板（只做 m2048）。
- 剪枝会使逐层增益变小，几十层后下溢成 0、混入激活稀疏，所以先乘一个增益（numpy 模拟，各层预激活均方根约 1）再交给 coremltools 剪枝（按绝对值排序，与缩放无关）。

**度量**：kdebug 驱动提交（61b01a9）→ 固件任务结束（61b0126）的中位数，取两种层数的斜率；M4 的 kdebug 没有固件任务事件，用调用耗时中位数。第一轮里部分 c1x1 剪枝运行的固件"开始"事件 61b0125 只记到 0–40%（结束事件齐全，原因未查明），所以不用任务时长。

2. 编译产物三处印证：
   - 卷积 TD 寄存器 0x1240 从 0x10000082 变为 0x182（第 28 位清、第 8 位置），推测是"权重为压缩稀疏格式"；
   - 0x1559–0x1567 是 16 个 NE 各自的权重偏移、0x1568–0x1577 是长度：稠密时每个 NE 都是 0x8000（32 KiB），剪 50% 后为 0x4740–0x4900，**各 NE 长度不同**；
   - 编译器性能模型 exe_cycles（单位约 1 µs）：c1x1 稠密每层 3，剪枝后每层 1。
3. **不需要结构化**：2:4 与非结构化剪 50%、1:4 与剪 75% 完全一样快。
4. 加速不到非零比例：0.5 / 0.25 / 0.1 的非零比例对应 0.66 / 0.42 / 0.36（M4 0.68 / 0.44 / 0.33）。可能来自各 NE 压缩权重长度不等（最慢的 NE 决定）、每层固定开销或解码速率，未分解。

c3x3（M6 中位数，两轮）：稠密 41–44 µs（Winograd，约 28–29 TFLOPS）；剪 50% / 2:4 为 46–47 µs（**比稠密慢 5–15%**）；剪 75% / 1:4 为 25.7 µs（0.59–0.63）；剪 90% 为 13.9 µs（0.32–0.34，按稠密乘加折合 87 TFLOPS）。
- 原因：**剪枝后编译器关掉 Winograd**（任务信息 0xf 第 27 位 1 → 0，OCG 2 → 16，每层 TD 从 6 个变 2 个），改为直接卷积 + 跳零。直接卷积稠密峰值约 57 µs / 层，剪 50% 只到其 0.8 倍，抵不过 Winograd 的约 1.4 倍。**3×3 层剪到 75% 以上才有收益**。
- c3x3 的任务时长有长尾（部分权重从 DRAM 读，DCS 下限 25–47 GB/s），平均值比中位数大 5–25%；版本之间的排序两种统计一致。
- M4 上 c3x3 的 4.7 MB 共享权重每层从 DRAM 重读（4.72 MB ÷ 70 µs = 67 GB/s），耗时只随字节数变（剪 90% 0.22–0.24），不能用来判断跳零。

### 3. 零输入：不跳过

第一轮发现只改输入行不通：偏置为 0 时全 0 输入每层都是 0，但"随机一半为 0""一半通道为 0"只影响第 1 层，之后被卷积混合；另用"逐层取分位点的负偏置"制造 75% / 90% 的 0，编译器因各层偏置不同而每层各存一份权重，混入读权重时间，作废。第二轮改为每层卷积后乘一个固定掩码（各层共享的常量，非零处取 [0.5, 1) 随机数，不能并入权重），图结构、权重完全相同，只改掩码中 0 的比例（每层输入 0% / 50% / 75% / 90% 为 0，或一半通道整体为 0）。

| 每层输入为 0 的比例 | M6 c1x1（32 → 64 层） | M4 c1x1（32 → 128 层） | M6 c3x3（16 → 32 层） |
|---|---|---|---|
| 0%（z00） | 4.51 / 4.52 µs | 5.04 / 5.29 | 43.7 / 46.0 |
| 50%（z50） | 4.40 / 4.40 | 5.17 / 5.01 | 46.1 / 43.4 |
| 75%（z75） | 4.40 / 4.40 | 5.04 / 4.97 | 39.5 / 45.3 |
| 90%（z90） | 4.40 / 4.40 | 5.13 / 4.91 | 45.5 / 44.5 |
| 一半通道为 0（zch） | 4.42 / 4.43 | 4.93 / 4.99 | 43.4 / 45.9 |
| 全 0 输入（fp16，第一轮） | 3.40（随机输入 3.41） | 4.24–4.28（4.27–4.38） | 42.6（37.6，漂移） |

（两个数为两轮；掩码模型比 fp16 每层多约 1 µs，是乘掩码的固定开销。）

1. **耗时与 0 的比例无关**：M6 c1x1 只有"有 0"与"没有 0"之间约 2.4% 的差（两轮一致），50% 到 90% 完全相同，不是按比例跳过；M4、c3x3 在噪声内（c3x3 ±6%，两轮方向不定）。整通道为 0 也不更快。
2. 因此 **14.4 节全 0 输入的 55.6 TFLOPS 不是激活零值跳过**。按本节，零权重能把按稠密折算的算力推到 2.5 倍以上，那个测评模型的权重若大量为 0（或被剪枝 / 初始化为 0）就能解释，需要回查那个模型的权重。
3. 13.3 节"卷积输入全 0 功耗 +7.5%"（power.md §7，`data/11_power/power_parts2`：6.73 / 6.84 W 对 6.31 / 6.27 W；PE 逐元素加全 0 则低 17%）**用的模型不是每层全 0**：`conv1x1_shared`（`tools/lib/bonded_cases.py`）的偏置为随机值（标准差 0.05）且层间 ReLU，所以只有第 1 层输入为 0，第 2–384 层的输入是 relu(偏置)，即每个通道一个非零常数、空间上处处相同。那 +7.5% 对应的是"空间上不变的激活"，不是零激活。本实验的模型偏置为 0，全 0 输入每层都是 0，只测了速度、没测功耗；真正全 0 时卷积功耗的高低未测。

### 4. 输出误差

`sparse_err.py`（M6，L16，同一剪枝模型、同一随机输入，ANE 对 CPU）：误差均方根 ÷ 输出均方根，c1x1 0.3–1.3%、c3x3 1–4%、m2048 0.1–1.9%，剪枝版本都不大于稠密版本（剪得越多累加项越少，误差越小）。ANE 执行剪枝模型与 CPU 一致。

### 5. 结论（报告用）

1. 剪枝权重在 ANE 上以"非零值 + 1 位掩码"存放并按压缩字节读入；读权重受限层的耗时与字节数成正比（M6 约 150、M4 约 67 GB/s），可与调色板叠加。【HWX】【kdebug】
2. M6 与 M4 的计算阵列都跳过零权重：权重在片上时剪 75% / 90% 按稠密折算达 47 / 54 TFLOPS（M6 单引擎直接卷积峰值 21.1）。每个 NE 拿一段长度不同的压缩权重。【kdebug】【HWX】【编译器】
3. 不需要结构化稀疏：2:4、1:4 与同比例的非结构化剪枝一样快。加速不到非零比例（0.5 → 0.66、0.25 → 0.42、0.1 → 0.36）。【kdebug】
4. 3×3 剪枝后不再走 Winograd，剪 50% 反而慢 5–15%，剪 75% 以上才有收益。【HWX】【kdebug】
5. 不跳过零激活：每层输入 0%–90% 为 0 的耗时相同（差 ≤ 2.5%，与比例无关）；14.4 节的 55.6 TFLOPS 应从零权重找原因。【kdebug】
6. 未查：加速不到非零比例的原因；0x1240 各位的确切含义；剪枝对模型精度的影响（本实验只测速度和 ANE / CPU 一致性）；全 0 输入的功耗。

## B2 / B3：输出通道数（OCG、NE 数）

1×1 卷积链，宽 128（单 ANE），通道数 C 从 192 到 1024，每 16 一档，共享权重。用 L=32 和 L=160 的斜率（相差 128 层）。数据：`data/05_compute/b2b_run.txt`。

| C | 每层耗时 | 边际吞吐 | 和上一档相比 |
|---|---|---|---|
| 240 | 0.97 µs | 15.2 TFLOPS | |
| 256 | 1.09 µs | 15.4 | +13% |
| **272** | **1.45 µs** | **13.1** | **+32%** |
| 352 | 1.82 µs | 17.4 | |
| 512 | 4.69 µs | 14.3 | |
| 528 | 5.26 µs | 13.6 | +12% |
| 768 | 9.09 µs | 16.6 | +3% |
| 784 | 9.57 µs | 16.4 | +5% |
| 1024 | 14.10 µs | 19.0 | +3% |

结论：
1. **只有 256 → 272 有一个明显的台阶。** 256 = 16 个 NE × 16，符合"每个 NE 每轮 16 个输出通道"。512 → 528 有一个小台阶（+12%），768、1024 处都没有。
2. 除此之外，耗时基本按 C² 平滑增长，吞吐从约 14 TFLOPS 逐渐升到 19 TFLOPS（C=1024，接近单 ANE 的约 20.6 TFLOPS）。M1 在 192→256 的耗时变成 3 倍；M6 上没有这样的陡台阶。
3. 可能的解释：
   - 宽 128 时输入张量很小（C=1024 时 256 KB），完全留在 L2 里，"多一轮就要重读一遍输入"的代价很小，所以台阶不明显。
   - 每次调用的中断数在 C≈416 时从 3 降到 2，说明编译器在这里换了分块或调度方式，和吞吐的波动对得上。
4. 局限：方形链里 Cin 和 Cout 同时变化。要单独看 Cout 的台阶，需要固定 Cin、单独改 Cout 的设计（例如 C→C' 和 C'→C 交替）。C < 192 时总时间被每次调用的固定下限盖住，测不准。

## B8：形状与 space_to_depth（对照 maderix Part 4 §4.9）

- 工具：`tools/05_compute/s2d.py`。
- 模型：1×1 conv + relu，32 层，共享权重。全部被切到两个 ANE。
- 原始数据：`data/05_compute/b8_s2d_run.txt`。

| 模型 | 耗时 | 吞吐 | maderix M4 |
|---|---|---|---|
| 64 通道、128×128 直接跑 | 450 µs | 9.5 TFLOPS | 3.92 |
| 64×128×128 → S2D(4) → 1024 通道 32×32 → D2S(4) | 2168 µs | **31.7 TFLOPS** | 16.37 |
| 直接输入 1024×32×32（不含 S2D） | 2149 µs | 32.0 | — |
| 64×128×128 → S2D(2) → 256 通道 64×64 → D2S(2) | 876 µs | 19.6 | — |
| 直接输入 256×64×64 | 874 µs | 19.7 | — |

结论：
1. 通道少、空间大的层效率很低（64 通道只有 9.5 TFLOPS）。S2D(4) 变成 1024 通道后到 31.7 TFLOPS，提高 3.3 倍。和 maderix 的结论一致：编译器按输出通道把工作分给 NE，通道少时 NE 用不满。
2. S2D + D2S 的开销：block=4 约 0.9%，block=2 约 0.1%（和直接输入的版本相比）。
3. **M6 上没有 maderix 说的 block=2 陷阱**（M4 上编译器把 S2D(2) 变成 one-hot 权重的卷积，开销 2.8–3.1%）。可以用编译产物确认 M6 的编译器是否换了实现。
4. 只有 S2D + D2S 的小模型被 Core ML 放到 CPU 上（0 中断），所以开销用"有 / 无 S2D"的差来算。

## B3：实际用了几个 NE

- 宽 8192（两个 ANE），通道数 16–256，L=32 与 L=128 求斜率，两轮。原始数据：`data/04_schedule/group1_run.txt`。

| 通道数 | 每层耗时 | 边际吞吐 |
|---|---|---|
| 16 | — | 总时间被固定下限盖住，不可用 |
| 32 | 1.17 µs | 14.3 TFLOPS |
| 48 | 2.19 µs | 17.2 |
| 64 | 2.84 µs | 23.6 |
| 96 | 4.77 µs | 31.6 |
| 128 | 10.1 µs | 26.6 |
| 192 | 16.9 µs | 35.7 |
| 256 | 33.9 µs | 31.7 |

- 编译产物：16、32、64 通道时，权重都切成 `_ne_0` … `_ne_15` 共 16 份。16 通道时每个 NE 分到 1 个输出通道。
- 结论：**只要输出通道数 ≥ 16，16 个 NE 全部启用**，输出通道平均分给各 NE。通道少时吞吐低（32 通道约为峰值的 36%），原因是每个 NE 分到的工作少（每个输出通道的输入通道也少，累加长度短），而不是有 NE 闲置。和论文"实际使用的核数 = min(num_nes, …)"的描述不同：M6 的编译器在通道数很少时也把 16 个 NE 都用上。
