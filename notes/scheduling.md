## D2：两个单 ANE 模型同时跑

模型：`k1x1_512_h1w128_L384`（1×1、512 通道、宽 128、384 层、共享权重）。它的编译产物里 bonded 版本也只有 ANE0 一个 kick，单独跑时只用 ANE0。

| 情况 | 每次调用中位数 | ANE0 中断 | ANE1 中断 |
|---|---|---|---|
| 单个进程 | 1598 µs | 2.00 次/调用 | **0** |
| 两个进程，同一个模型文件 | 1795 / 1799 µs | ≈2.84 | **≈2.83** |
| 两个进程，两份文件（已预编译），第 1 轮 | 1751 / 1755 µs | ≈2.5 | ≈2.5 |
| 两个进程，两份文件，第 2 轮 | 1796 / 1799 µs | ≈2.84 | ≈2.84 |
| 两个进程，两个不同模型（L384 + L256） | 1825 / 1388 µs | 有 | 有 |

（IOReport 的计数是全系统的，所以两个进程看到的中断是两个进程加在一起的。）

结论：
1. **并发的请求会被分到两个 ANE 上并行执行。** 单独跑时只用 ANE0 的模型，两个进程同时跑时 ANE1 也有同样多的中断，而每次调用只慢 12%，没有翻倍。
2. 两个进程合计吞吐约为单进程的 **1.78 倍**（2 × 1598 / 1797）。
3. 这和 Bryngelson 反编译得到的内核 LoadBalancer 行为一致："以整个提交为单位，派给最空闲的引擎"。所以 M6 有两种用法：
   - **一个大模型**：编译器生成 bonded 程序，按空间切到两个引擎（1.92×，见 `bonded_measure.md`）；
   - **多个请求**：内核把每个提交派到空闲的引擎（1.78×）。
4. 并发时每次调用慢 12% 的来源（主机侧开销、DRAM、固件）还没分清。
5. 第一次测"两份文件"时，ANE1 没有中断，耗时也没有翻倍。原因是第二份文件首次加载要先编译，两个进程的测量时段没有重叠，不是调度行为。
6. `bonded_measure.md` §1 里"没看到单 ANE 模型被放到 ANE1"只对单个进程成立。

### D2b：读权重受限的模型（2026-10-04，e6bc8dc）

| 模型 | 单进程 | 两进程 | 合计吞吐 | 任务时长 单 → 双 |

## D3 / D4：单元之间能否重叠（MAC、PE、重采样、DMA）

- 工具：`tools/04_schedule/overlap.py`（模型）、`tools/04_schedule/texprobe.py`（找能上 ANE 的采样类运算）。
- 原始数据：`data/04_schedule/d3_overlap_run.txt`、`data/04_schedule/d3_overlap_run2.txt`（两轮，每个模型 500 次）。
- 张量都是 [1, 512, 1, 128]。各支路：
  - A：1×1 卷积链（MAC）；
  - B：逐元素链 `y = y·u + u`（PE）；
  - T：双线性上采样 ×2 再平均池化缩回（推测走重采样 / 纹理单元，平均池化可能走 PE）；
  - D：32 MB 输入的一次转置（几乎不算，主要是 DMA 搬运）。
- 同一个模型里放两条互不依赖的支路（并列），与各自单独跑比较。判断时扣掉每次调用约 150 µs 的固定开销：
  - 完全串行的预测 = X + Y − 150；
  - 完全重叠的预测 = max(X, Y)。

| 组合 | X 单独（p10） | Y 单独 | 完全重叠的预测 | 完全串行的预测 | 实测并列（两轮） |
|---|---|---|---|---|---|
| MAC + PE（A64 + B64） | 374 µs | 224 µs | 374 | 448 | **486–490** |
| MAC + PE，A64 的输出接给 B64（串行对照） | | | | | 455–456 |
| MAC + 重采样（A64 + T64） | 374 | 305 | 374 | 529 | **542–583** |
| DMA + PE（转置 + B64） | 1167 | 224 | 1167 | 1241 | **1277–1341** |
| DMA + MAC（转置 + A64） | 1167 | 374 | 1167 | 1391 | **1387–1391** |
| matmul（8 层）+ 一个独立 relu | 178 | | | | 206（+28 µs） |

结论：
1. **独立支路一律串行执行。** 没有任何一组接近"完全重叠"的预测，实测都在串行预测上或略高；DMA + MAC 和串行预测吻合到个位数。比串行还慢的几组，推测是多一个输出就多一次写回，或者并列时双 ANE 的切分方式变了（B64、T16 单独跑时用两个 ANE，组合后变成单 ANE）。
2. 但**同一层内部有流水线重叠**：
   - conv + bias + relu 融合成一个硬件层；
   - 读下一层权重的 DMA 与计算重叠（`memory.md` C2：每层计算 4 µs、读 0.5 MB 权重 3.6 µs，几乎不慢）；
   - 长链按块融合，中间结果不回 DRAM（`memory.md` C1）。
3. 合起来的模型：**任务描述符按顺序逐个执行，同一时刻只有一个；重叠只发生在一个任务内部的 DMA → MAC → PE → 写回流水线上**。和 maderix 在 M4 上的测量一致（独立支路只省约 1%）。论文从编译器推测的"MAC 和 PE 可以同时发射"（co-issue），在这些结构里没有观察到。
4. **softmax 与卷积也不重叠（D4）**。单独的 softmax 链会被放到 CPU 上，所以用"卷积链的输出接给 softmax"（串行）作基线。两轮 p10：并列 446.0 / 446.0 µs，串行 445.6 / 445.6 µs，完全相同；只有卷积链是 368 µs。论文推测的"MAC 和 PE 可以同时发射（softmax 与 matmul 并发）"在这种结构里没有出现。数据：`data/04_schedule/group1_run.txt`。

### 其他观察

- **8 个串联的逐元素运算几乎不花时间**：add8_ser（陪跑 16 层卷积 + 8 步 `y·1.001 + u`）的 p10 是 198 µs，只有陪跑支路的 side16 是 206 µs。推测这 8 步被融合进了同一次 PE 处理（chaining）。8 个独立的 add（8 个输出）要 239 µs，多出的约 33 µs 来自 8 次输出写回。
- **32 MB 转置约 1.0 ms**（扣掉固定开销），64 MB 读写折合约 60 GB/s。数据重排的带宽远低于读权重的 150 GB/s。
- **能上 ANE 的采样类运算很少**：16 步链的 resize_bilinear、最近邻上采样、gather 都被放到 CPU 上，只有 upsample_bilinear + avg_pool 在 ANE 上。
- 单纯的逐元素链和重采样链，有时会被切到两个 ANE（B64、T16），有时只用一个（T64）。决定切不切的规则不只看宽度，还和算子类型、层数有关。

## D5：图深度上限

- 模型：64 通道、宽 1024 的 1×1 卷积链（每个张量 128 KB，和 maderix 的设置相同），共享权重。
- 原始数据：`data/04_schedule/d5_depth_run.txt`、`data/04_schedule/d5d6_run2.txt`、`data/04_schedule/d5_depth_m4.txt`。

| 层数 | M6 | M4（同一个 macOS 27、同一个 .mlmodelc） |
|---|---|---|
| 64–384 | ANE（两个 ANE 都有中断），191–309 µs | 383、384 层：ANE，约 2.0 ms |
| 385、386 | ANE，约 330 µs | 386 层：ANE |
| **387** | **加载时卡住**：计时进程等了 11 分钟以上，CPU 为 0，编译服务空闲，既不报错也不退回 CPU | ANE |
| 388 | **退回 CPU**（0 中断，26.9 ms） | ANE |
| **392** | **卡住**（同 387） | — |
| 400–1024 | 退回 CPU（27–70 ms），不报错 | 400、448 层：ANE（未测更深的） |

结论：
1. **M6 上的上限是 386 层**（这种张量大小下）。超过以后，Core ML 一般不报错，而是悄悄退回 CPU，慢 100 倍以上。
2. **紧挨着上限的个别层数（387、392）会让加载过程挂住**，既不跑 ANE 也不退回 CPU。实用上要和上限留出余量。
3. **同一个系统、同一个模型文件，M4 能编得更深**（至少 448 层）。所以上限和芯片有关，不是编译器的统一规则。maderix 在 M4、旧系统上测到"383 可以、384 编译服务断开"，和现在的 M4 也不一样，说明也和编译器版本有关。
4. **原因已查明（H9）：编译器栈溢出。** 用 `anecc` 直接编译同一个模型（数据：`data/03_compile/h9_depth_compile.txt`）：

   | 层数 | h16g | h18 | h18g |
   |---|---|---|---|
   | 384、386 | ✅ 208 KB | ✅ 208 KB | ✅ 512 KB |
   | 387、388、400、512 | ✅ | ✅ | **崩溃，返回码 138（SIGBUS）** |

   - 崩溃报告：`EXC_BAD_ACCESS / SIGBUS`，地址在线程栈的保护页（"Could not determine thread index for stack guard region"），即**栈溢出**。
   - 调用栈：`ZinIrOpLayerGraphScheduler::Schedule` 层层递归（每层网络一层递归），在 `ZinIrScheduleGraph::CompressAttentionBlockBranches` → `ZinIrParallelExecutionOpportunityFinder::FindIntraANEParallelism` → `FindAllAttentionBranchesInRegion` → `ZinIrNgraph::TopologicalSortImpl` 里把栈耗尽。
   - 这个"找可并行的注意力分支"的步骤只在 h18g 上执行，单引擎目标不走这条路，所以 h16g / h18 编到 512 层也没事。
   - 所以 **M6 的 386 层上限是编译器的递归深度问题（软件），不是硬件限制**。在 Core ML 路径里，编译服务崩溃后的表现不确定：有时退回 CPU，有时调用方一直等下去（387、392 层的卡死）。
   - maderix 在 M4 旧系统上看到的"384 层编译服务断开"，很可能也是同类的编译器崩溃。

### D1c："任务以外每层约 0.48 µs"的来源（2026-10-03）

- 问题：D1 只用 16 层和 384 层两个点，得出"任务以外 = 150 µs + 每层 0.48 µs"。D6b 发现小层不按层数增长，memory.md C2j 发现主机侧唤醒开销随任务时长变化。这里把"层数"和"任务时长"分开。
- 设计：两组单 ANE 的 1×1 链（宽 128，共享权重），任务时长范围相同、层数相差 4 倍：
  - A = 512 通道，16–384 层；
  - B = 1024 通道（每层计算量是 A 的 4 倍），4–96 层；
  - 另对 A 的 16、96、384 层在 12 个 nice 20 空转进程下各测一次（CPU 无法深度空闲）。
- 工具：`tools/04_schedule/d1b_ktrace.sh`（kdebug 0x061b，只读）、`tools/04_schedule/d1b_stages.py`。数据：`data/04_schedule/d1b_kt/`、`data/04_schedule/d1b_stages.txt`、预热 `data/04_schedule/d1b_warm.txt`。单 ANE 时固件不发任务开始事件，所以按"提交 → 任务结束"和"任务结束 → 下次提交"两段拆。

| 模型 | GFLOP | 调用 | 提交 → 任务结束 | 任务结束 → 下次提交 | 其中驱动完成 | 用户线程返回 |
|---|---|---|---|---|---|---|
| A L16 / B L4 | 1.07 | 227 / 212 | 80.2 / 80.9 | 147 / 131 | 21 / 21 | 81 / 64 |
| A L32 / B L8 | 2.15 | 263 / 268 | 134.6 / 136.4 | 128 / 129 | 32 / 32 | 51 / 50 |
| A L64 / B L16 | 4.29 | 371 / 422 | 243.7 / 252.3 | 127 / 167 | 32 / 33 | 47 / 88 |
| A L96 / B L24 | 6.44 | 503 / 550 | 351.2 / 361.3 | 153 / 183 | 41 / 55 | 60 / 81 |
| A L128 / B L32 | 8.59 | 710 / 752 | 448.4 / 472.2 | 255 / 278 | 88 / 92 | 111 / 134 |
| A L192 / B L48 | 12.88 | 992 / 1012 | 664.4 / 692.8 | 326 / 317 | 109 / 108 | 156 / 155 |
| A L256 / B L64 | 17.18 | 1200 / 1233 | 869.1 / 912.6 | 325 / 320 | 109 / 109 | 156 / 155 |
| A L384 / B L96 | 25.77 | 1618 / 1676 | 1292.8 / 1358.2 | 324 / 318 | 106 / 105 | 157 / 154 |
| A L16 / L96 / L384，空转 | | 220 / 565 / 1698 | 80.6 / 374.5 / 1471.3 | 139 / 189 / **215** | 28 / 40 / **41** | 74 / 108 / 126 |

结论：
1. **ANE 一侧没有"每层开销"**：提交 → 任务结束对计算量是一条直线，A 为 30.8 µs + 49.0 µs/GFLOP，B 为 27.5 µs + 51.6 µs/GFLOP，残差都在 ±5 µs 以内。若每层另有 0.48 µs，A 在 25.8 GFLOP 处比 B 多 288 层，应多约 138 µs，实测 A 反而少 65 µs（1024 通道的层效率略低）。截距约 30 µs 是提交到任务开始的固定延迟加上每次调用的固定部分。
2. **任务结束后的开销随任务时长变化，与层数无关，并且会饱和**：任务时长 ≤ 约 350 µs 时约 127–150 µs；之后上升；任务 ≥ 约 660 µs 时稳定在约 320 µs。A 和 B 在相同任务时长下几乎相同，A 的 192、256、384 层都是约 325 µs，B 的 48、64、96 层都是约 318 µs。
3. **增长全在主机侧的两段**：固件发消息、中断、完成标记三段合计一直约 45–50 µs，不变；驱动完成处理从约 21–32 µs 增加到约 106 µs，用户线程返回从约 50 µs 增加到约 156 µs。这就是 memory.md C2j / defects.md B5 的 CPU 深度空闲效应。
4. **让 CPU 无法深睡时，饱和值从 324 µs 降到 215 µs**（384 层），驱动完成处理从 106 µs 降回 41 µs。用户线程返回仍偏长（126 µs），是因为 12 个空转进程与测试线程争抢 CPU，这个对照只能说明方向。
5. **对 D1 的更正**：16 层（任务约 60 µs）落在平台下段（约 150 µs），384 层（任务约 1270 µs）落在饱和段（约 325 µs）。两点连线得到的"每层 0.48 µs"是假象，实际是"任务时长从短到长时，主机唤醒从浅睡变成深睡"，与层数和描述符处理无关。正确的描述是：每次调用在任务之外约 30 µs（提交侧）加上 130–325 µs（结束侧，取决于任务时长是否超过约 350 µs）。

## H15：同一进程内的并发（2026-10-02）

- 工具：`tools/common/mtrun.m`。多线程同时调用；每组可以共用一个 MLModel，也可以每个线程各自加载一份。所有线程先各自预热 1 s，然后同时开始，连续跑 5 s。IOReport 统计两个 ANE 的中断。

结论：
1. **在同一进程里，同一个编译后的程序同一时刻只执行一个请求**。多开线程、多加载几个 MLModel 对象都没用：吞吐不变，耗时按线程数成倍增加，全部在 ANE0 上。
2. **同一进程里不同的程序可以并行**：A + C 合计 1249 次/s，是两者单独跑的 616 + 843 的 86%。内核把其中一个派到了 ANE1，每次调用各慢约 13%，和 D2 中两个进程的 12% 一致。
3. **不同进程里的同一个模型可以并行**（1.81×），和 D2 一致。所以串行的单位是"进程 × 程序"。推测原因：aned 按"连接 + 缓存键"共用同一个已加载的程序（日志里的 `programHandle`），而同一个程序的请求在驱动里排成一个队列。
4. bonded 模型占用两个引擎，和单 ANE 模型混跑时也有约 25–30% 的收益（762 次/s，对比两者单独跑的 587、616）。单 ANE 模型的请求进入了 ANE1，可能是填补了 bonded 任务两侧不对称留下的空闲，以及任务之外的固件开销。
5. 实用含义：
   - 在 M6 上，想让两个单 ANE 模型同时占满两个引擎，要么用不同的模型（程序），要么分到不同的进程；
   - 用同一个模型开多线程不会有任何加速。
   - 多个线程之间严格轮流执行：各线程的调用数相差不到 1。

## H54：固件和驱动如何调度任务、谁来选时钟档位（2026-10-03）

方法：只读分析 M6 上已解包的 ANE 固件（`~/anehal/fw/h18_ane0_fw_kirkland_j8xx.bin`，RTKit Mach-O，`__TEXT` vmaddr 0 = 文件偏移 0x4000）和 kernelcache（`~/anehal/kc/kc.bin`，字符串表 `kc_strings_off.txt`）。工具：`tools/re/fwref.py`（找引用某地址的指令）、`tools/re/fwfunc.py`（带字符串注释的函数反汇编）。只依据字符串、断言和少量反汇编，**不运行、不修改**任何固件或驱动。

### 1. 三层结构

| 层 | 组件 | 作用（依据） |
|---|---|---|
| 主机内核 | ANE 驱动（`H11ANEInUserClient` / `AppleH1xANEInterface`） | 优先级映射、选引擎（ANE0/1、bonded 或单 ANE 变体）、依赖（fence）、节流、电源开关、向 CLPC 报告工作 |
| 主机内核 | **CLPC**（`AppleCLPC`：`ane_job_tracking`、`ane_perf_sampler`、`ane_forced_idle_limiter`、`ane_topology`） | **决定 ANE 的时钟档位**和节流比例 |
| ANE 内 | 固件（`AppleH16AneFW` 源码树：`sne/aneEngine/exeLoop`、`sne/drivers/tm`、`itq`、`mcw`、`PowerControlService`、`CLoadMonitor`） | 按优先级排队、把请求下发到硬件任务队列、动态电源门控、上报 IOP 负载 |

### 2. 驱动：请求进入、优先级、选引擎

- 每个请求带 `priority` 和 `qos`（`programHandle … priority: %u, qos: %u`）。
  - 逻辑优先级经 `applyFirmwarePriorityMapping` 映射到固件优先级（`Logical priority %u has no firmware mapping for this SoC`），超出上限的会被截断。
  - 最高的 `kANEFirmwareProgramPriority0` "固件尚未支持"，会退回到较低一级。
  - 授权 `com.apple.ane.realtime-priority-client`、`com.apple.ane.allow-system-reserved-priorities` 给实时或系统优先级。
- 防饿死：`Low-priority starvation threshold set to %u ms`、`shouldYieldToLowerPriorityRequest`、`firmwareResourceIsAvailableForPriority`；按优先级统计已提交请求数和执行时间（`...SubmittedRequestsCountAndExecutionTimePerPriority`）。
- 依赖：`fence LocalStrict` / `LocalFast`。前序请求执行中时，后续请求可以先提交（LocalFast），或者挂起等待（LocalStrict）。
- **选引擎** `SelectBestANECore prio %u … numANEs %u`，每个引擎打一个综合分：`WRK`（已排队的工作）、`HOL`（该优先级的队头阻塞比例，`holRatio` → `weightedNormalizedHolRatio`）、`CLPC`（CLPC 推荐的允许簇 `allowedClusters`）、`THROT`（该引擎被节流的百分比）、`clientPref`（客户端指定 ANE0/1 的提示）、`PWR`（是否已上电）。之后由 `ANEProcedureVariantSelector` 选 bonded 或单 ANE 变体（`debugANE … requires program to have single-ANE variant`）。与 H15、D2 的现象一致：同一程序的请求由驱动分到引擎，不由用户决定。
- 会话提示：`kANEClientHintTypeSessionStart/Stop/Abort`、`ANEClientEnergyEfficientWorkload`（"节能负载"提示，推测会让 CLPC 选低档），以及客户端可设的断电计时器周期（`Client passed 0 … disabling sleep timer`）。

### 3. 固件：队列和下发

- 固件优先级 `fwPriority < 6`（6 级）；作业队列 8 个，另加一个专给 AFPP（ISP 的 ANE 网络）的队列（`foundQueue == 8 + 1`）。命令优先级断言为 1–5 或 2–7（不同命令格式）。
- 调度信息表 `scheduleInfo[queueId]`：`AddScheduleInfo`、`AvailableScheduleInfo`、`Found Matched Priority Q[%d]S[%d]`。按优先级找到可用的队列和槽位后，把请求放进**硬件任务队列 TQ**（`Set TQ[%d] priority`、`Set ITQ[%d] priority`）。
- **每个 TQ 有两个槽**（`reqRunning[index][0/1]`、`check HW slot … [0]=%d, [1]=%d`）：一个在执行，下一个已就位。这是固件层面的双缓冲，与 D1"固件开销约 45–50 µs、两次调用可以首尾相接"一致。
- **可以切换或抢占**：`Clear switched out req`、`should not have switched out request when ANE is idle`、`Pending deprioritize commands present for dsid`。硬件任务管理器（`CSneTMDrvH18g`）在不同优先级的 TQ 之间切换。驱动会下发"上下文切换延迟阈值"（`CSNE_CMD_ANE_DEFAULT_SETTING_SET for setting Ctx Switch Latency Threshold`），内核还统计 `CtxSwitch Latency Histogram`。推测高优先级请求到来时，会在 TD 边界换下低优先级任务；阈值的具体值未读出。
- 低延迟直通路径：`Direct path should be executed when everything is idle`。
- **固件不选时钟档位**：
  - 固件只有 RTKit 通用的 PSD（power state domain）投票接口（`_getPowerStateVote`、`clientId … serviceId … pstate`），用于 ANE 自身各电源域的开关；
  - 还有一个 `PerfMode` 属性（驱动通过 `CSNE_CMD_CH_PROPERTY_WRITE for setting FW perf mode` 写入）；
  - 另有一个查表函数（`0x89f34`，失败时打印 "Latency to P State Translation Failed"），把延迟要求换算成档位号：从第 6 档（另一模式为第 1 档）往低查，表在 `__DATA 0xc87b8`，运行时填充。推测用于固件内部某个电源或 PSD 域，未见它与 NE 时钟相连。
  - 固件中没有 NE 频率表（compute_array.md 已核对）。
- `CLoadMonitor`：固件上报 **IOP 自身的 CPU 负载**（`CSNE_CMD_CPU_LOAD_NOTIFICATION` / `_GET`）。驱动据此运行 `ANECPULoadThrottler`：负载高（≥ 高水位）时暂停高优先级通道，中等时限流为 1，低时不限（`CPU Load HIGH/MEDIUM/LOW`）。这是防止 IOP 被命令淹没的机制，不是调频。

### 4. 调频：CLPC 决定，驱动报告工作

- 驱动注册为 CLPC 的 `IOPerfControlClient`（`Registering with PerfControl with %u tokens`；拿不到时打印 "running without CLPC"）。每个请求经 `submitWorkToPerfController`、`workBeginForThrottling`、`notifyPerfController` 报告开始和结束，`notifyPerfControllerOfFutureWork` 预告即将到来的工作。
- CLPC 侧 `ane_job_tracking` 跟踪 ANE 作业，`ane_perf_sampler` 采样 ANE 性能计数器和降频计数，`ANE%uFrequencies` 和 `_anePerfStateFrequenciesMHz`（32 档）来自 PMGR。CLPC 据此选 NE 档位，ANE 共享簇（PE / L2，compute_array.md B10）单独调。
- **节流（功耗或温度）也由 CLPC 定比例、驱动执行**：
  - 驱动向 CLPC 查"节流百分比"（`Throttling: … querying CLPC`，带缓存和过期时间）；
  - 再用**占空比窗口**执行：`Duty cycle windows calculated: throttle=%d%% active=%ums inactive=%ums period=%llums`、脉冲计时器（`ANEHWThrottlePulseTimer`）、自适应预算（`budget exhausted (consumed … allowed …), setting inactive`）。
  - 即**降频之外，还会让 ANE 停一段、做一段**；节流期间还会打开动态电源门控的滞后计时器。
  - 本机 5 分钟满载没有触发任何节流（power.md §4）。

1. **CLPC 是利用率控制器，目标约 76–77% 忙**：

4. 档位在稳态也会在相邻几档之间跳动（G = 150 时 1548–1872 MHz 都有），符合闭环控制的抖动。
5. 实际意义：
   - 只要每次调用之间的空闲超过约 25%，CLPC 就会降频，把空闲压回约 23%。所以**主机开销越大，ANE 跑得越慢**：每次调用固定约 380 µs 的空隙，单次 ANE 时间 ≤ 约 1.3 ms 的模型，即使连续调用也只能在 77% 附近徘徊。
   - 低延迟需要减小任务之间的空隙，例如异步或批量提交、多个请求并行排队（H15 多进程），而不是指望 CLPC 自动拉满。
   - 能耗角度，低档的每次推理能耗约为满频的 1/3（power.md §7.4，低档就是 852 MHz）。

**降档**（2580 → 852 MHz，A 组 6 次）：
- 先在 ≥ 2448 保持 17、32、42、0、47、48 ms（0 的那次切换前只有约 2112）；中位轨迹 30 ms 约 2406 → 50 ms 约 2238 → 75 ms 约 1794 → 100 ms 1548 → 约 150 ms 852；
- **138–167 ms 降到下限**（不在顶档出发的那次 94 ms），与升档速度相当；
- 最后一步常从约 1548 直接跳到 852。

**降到中间档**（0 → 200 µs，B 组 5 次）：
- 先在 ≥ 2448 保持 160–230 ms（1 次约 29 ms），再经数百毫秒大致稳定在 1188–1548 MHz，过程中来回摆动；
- 从中间档回到 ≥ 2448 MHz：125–141 ms。

**空闲后的时钟**（C 组，满频运行后完全空闲，按实际间隙）：

| 空闲 | 恢复后第 1 个任务的档位 | 回到 ≥ 2448 MHz |
|---|---|---|
| 14 ms（预热结束后的间隙，非设定） | 2508 MHz | 立即 |
| 30 ms | 2196 | 约 110 ms |
| 60 ms | 1968 | 约 190 ms |
| 111 ms | **852**（下限） | 约 0.29–0.36 s |
| 212 ms | 852 | 约 0.25 s |

- 空闲时档位也在衰减：约 30 ms 降 5–6 档，**约 100 ms 降到下限**。与 power.md §3"空闲 0.1–3 s 后第一次调用多约 4 ms、要再连续跑约 0.3 s 才回到稳态"一致。
- 空闲后的恢复比 A 组的阶跃升档慢。推测是因为 CLPC 的利用率估计要先把空闲期"冲掉"，属于带记忆的平均。

**解读**：CLPC 对 ANE 是一个利用率控制器，升降速度取决于利用率与目标的偏差，不是"升快降慢"：
- 同步调用的主机空闲（约 390 µs）下，从下限升到 ≥ 2448 MHz 通常 100–200 ms，空闲较短时可快至约 55 ms；
- 降档先保持 17–48 ms，再用约 100–150 ms 降到下限；
- 目标落在中间档时，收敛需要几百毫秒，并伴随摆动；
- 具体增益和平滑常数没有从代码中读出。

**实际意义**：
- 间歇推理，例如每帧之间空闲超过约 30 ms，每帧开头都会在较低档运行，第一次调用变慢；空闲超过约 100 ms 则从 852 MHz 起步。
- 基准测试至少要预热约 150–200 ms 的连续负载，最好 ≥ 1 s，且不能插入空闲。

### 8. 77% 只在空闲短时成立：三轮验证（2026-10-04）

检验报告 12.4 节的推断（平衡利用率与任务长短无关；按驱动区间算目标恰为 80%）。工具 `tools/10_clpc/gov_target{,2,3}.sh`、分析 `gov_target_fit.py`、`gov_target2_fit.py`（gov_tg2 / gov_tg3 共用）；数据 `data/10_clpc/gov_tg{,2,3}/`（trace 只保留 61b0125/0126/01a9/00a0/0071，第二、三轮带 cpu 列区分引擎）。每段固定运行 12–16 s，丢弃前 4 s。

模型（`chain.py` 生成在 M6 的 `gt/`，满频单次任务时长）：
- S：单 ANE、权重在片上，512 通道 384 层，1.3 ms（原模型）。
- M：单 ANE、读 DRAM，1024 通道 96 / 192 / 384 层，1.3 / 2.7 / 5.3 ms（384 层时约 150 GB/s，满频受内存限制；1024 通道权重 2 MB 已不留在片上，512 通道 0.5 MB 留在片上）。
- B：两个 ANE 并行（bonded）、权重在片上，512 通道 384 层、宽 256 / 512 / 1024，1.4 / 2.6 / 5.2 ms。
- 第一轮另有 2048 通道 384 层（单 ANE，读 DRAM，21 ms）。
- 顺带发现：512 通道超过 384 层、1024 通道 768 层以上，编译器不放上 ANE，Core ML 静默回退 CPU；宽 ≥ 256 被拆到两个 ANE。

**结果（固件口径，排除被 2580 / 852 MHz 卡住的点）**

| 每次空闲（含主机开销） | 忙碌比例 | 模型 |
|---|---|---|
| ≲ 1 ms | 75–78% | S、M、B 全部，任务 1.9–3.7 ms |
| 2.6–2.9 ms | 65–68% | M 2.7、B 2.6、B 5.2 |
| 3.5–4.1 ms | 60–64% | M 2.7、M 5.3、B 2.6、B 5.2 |
| 4.7–5.3 ms | 58–59% | M 5.3、B 5.2 |
| 7 ms | 56% | M 5.3、B 5.2 |
| 10 / 14 ms | 53% / 50% | B 5.2（1221 / 1009 MHz） |

1. **任务一长、空闲一长，忙碌比例就低于 77%，而时钟远未到下限**（例如 B 5.2 在 7.3 ms 空闲时 56%、1505 MHz）。纯利用率控制器会继续降频，所以 CLPC 不是单纯把忙碌比例压到 77%。
2. **不是 DRAM 造成的**：权重在片上的 B 组与读 DRAM 的 M 组偏离程度相同。
3. **与"空闲 ÷ 任务"的比例无关**，主要随空闲的绝对长度变化；同样空闲下任务越长，忙碌比例略高。第一轮"与时间尺度无关"的印象是巧合。第一轮 2048 通道模型在 12–24 ms 空闲时的 61–67% 是读 DRAM 模型的特例；权重在片上的模型曲线单调下降，直到时钟到下限。
4. **"按驱动区间算恰为 80%"不成立**：空闲短时驱动口径 79–82%，空闲一长它也降到 57%，没有哪个口径保持恒定。驱动区间比固件任务多出约 80–180 µs（`61b01a9` → `61b00a0`）。
5. **一个近似模型**：CLPC 用时间常数 τ 的指数平均跟踪忙碌，在每个作业结束时取值与目标比较。周期性忙 d、闲 g 时，结束时刻的取值为 (1 − e^(−d/τ)) / (1 − e^(−(d+g)/τ))，空闲越长越高于真实忙碌比例，所以 CLPC 不再降频。对 28 个未卡住的点联合拟合：目标约 80%、τ ≈ 6.5 ms，均方根误差 2.9%（目标固定 77% 时 τ ≈ 8.2 ms、3.2%；把忙碌比例本身当被控量为 9.0%）。空闲 10–14 ms 的两点残差 +5% / +8.5%，长空闲下真实 CLPC 偏得没这么多，所以这只是方向正确的近似，不是 CLPC 的算法。
6. **另一种工作状态**：B 宽 256（满频 1.4 ms）在空闲 ≥ 约 2.5 ms（G = 800–1300 µs，G = 1050 重复三次）时稳定在约 2540 MHz、忙碌比例 32–36%；空闲约 2.4 ms（G = 700）时还在约 910 MHz、58%。其他模型在类似空闲下没有这种跳变，原因未知。
7. **主机停顿**：个别段里调用线程会整半秒几乎不发请求（第二轮宽 256 G = 700、宽 512 G = 540，第三轮宽 512 G = 600）。分析脚本按 0.5 s 窗口剔除任务数不到中位数一半的窗口（"剔停顿"列）；有停顿的段只看这一列。

**对报告的影响**：12 章开头"CLPC 把忙碌比例稳定在约 77%"、12.4 节三条推断都要改为"空闲 ≲ 1 ms 时成立"；6 章"主机开销越大、档位越低"的结论在短任务下仍成立。
