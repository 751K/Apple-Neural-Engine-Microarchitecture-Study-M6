# maderix Part 4 精读：《The Complete Machine》

原文：https://maderix.github.io/articles/inside-the-m4-ane-part-4/ （2026 年 8 月）

每条结论都标出它的证据来源，方便判断哪些可信、哪些能在 M6 上复现：

| 标记 | 证据来源 |
|---|---|
| 【HAT】 | 编译器的硬件参数表 |
| 【HWX 对比】 | 编两张只差一个属性的图，比较二进制 |
| 【HWX 修改】 | 改二进制里的字段后上机执行，看输出或耗时 |

## 1. 方法

- **两条路径**：
  - MIL → 编译器 → ANE：能看到算子支持、整图性能、编译器策略；看不到编译器选了哪些描述符字段。
  - HWX → loader → ANE：能看到任务描述符（TD）、DMA 记录、分块、模式、同步；看不到固件内部，也没有性能计数器。
- **认定一个字段含义的标准**：改了这个字段之后，程序能加载，并且输出或耗时按预期变化，才算认定。
- **第二重验证**：从零生成的程序和编译器的输出逐字节一致，跑到实测峰值的 98.8%。
- **HAT**：在运行中的 M4 编译器进程里，用 LLDB 调用 `ZinIrHalH16g::GetParams()`，取出 2360 字节。
- **字段命名**：HAT 字段名和编译器内部 pass 的名字来自 Bryngelson 的论文（覆盖 A11 到 M5）。

## 2. 程序从编译到执行的全过程（图解 9 步）

1. **MIL**：`program(1.3)`, `func main<ios18>`，这一例子只有 conv → add → relu 三个算子。
2. **校验**：每个算子过一遍 `_ANECValidate*Layer`。
3. **融合**：conv+bias+relu 合成 1 个硬件层，编译器内部类名 `ZinNEBypassLayer`。
4. **合法化和分块**：4 MiB 的操作数按 HAT[0x1b8] = 2 MiB 切成两块。
5. **调度**：生成任务描述符序列，比如 TD0 load、TD1 conv、TD2 conv、TD3 store。
6. **内存分配**：SRAM 按 ⌊addr/16⌋ mod 64 分配 bank，编译器选择行步长，避免 bank 冲突。
7. **生成 HWX**：Mach-O 格式，magic 0xBEEFFACE。
   - `__TEXT`：任务描述符流
   - `__KERN_0`：权重和 LUT
   - `__FVMLIB` × 2：输入、输出描述
8. **加载**：
   - aned 守护进程缓存 HWX（`com.apple.aned/…/model.hwx`）；
   - IOKit 设备是 `AppleH16ANEInterface`；
   - 通过 DART 映射到设备虚拟地址，页大小 16 KiB。
9. **执行**：
   - 编译和加载走 aned 的 XPC；**执行不经过守护进程**，直接走 `ANEServicesProgramProcessRequestDirect`；
   - 主机发一条 mailbox 命令，引擎执行整张图，结果写进 IOSurface。

## 3. 硬件框图（他给出的结构）

```
DRAM 120 GB/s（操作数超过 2 MiB 就流式读写）
  ├─ tile DMA 0 / 1 / 2      ← 编译出的程序里引用 3 个
  └─ kernel DMA（16 块）     ← 引用 1 个
        ↓
SRAM scratchpad：64 bank，16 B 交错，没有替换策略（编译器自己管理）
  └─ 权重存储：64 KiB 常驻，最多 16 MiB 流式读入
        ↓
MAC 阵列：8 个计算组 × 8 个累加器，FP16
        ↓
平面引擎（planar engine）：ALU、33 点 LUT、归约；relu 直接走 ALU，不用 LUT
        ↓
IOSurface 输出（CPU 和 GPU 可以零拷贝读取）
```

## 4. 各项结论和证据

### 4.1 设备身份 【ioreg】【HWX 对比】

- `AppleH16ANEInterface`，架构 h16g，版本 192，登记了 16 个核。"G" 的含义未确认。
- HWX 的 CPU type 是 0x80，subtype 是 0x07（H16G）。

### 4.2 2 MiB 规则 【HAT】【HWX 对比】

- 编译器拿**每个操作数**和 HAT[0x1b8] = 2 MiB 比较。不是按单个运算比，也不是所有操作数加起来比。
- 不超过 2 MiB：先整块读进来再计算，读的时候阵列空闲。
- 超过 2 MiB：分块、双缓冲，第 n+1 块的读入和第 n 块的计算重叠，只有第一块的读入时间露在外面。
- **修正了 Part 2 的结论**：Part 2 在 24–32 MB 处看到的性能下降，来自分块流式读写，并不说明 SRAM 总容量就是 32 MB。

### 4.3 SRAM 【HWX 对比】

- 64 个 bank，交错粒度 16 B，bank = ⌊addr/16⌋ mod 64。
- 编译器选一个和 64 互质的行步长，让连续 8 行落在 8 个不同的 bank 上。
- 权重：64 KiB 常驻（"kernel-coefficient store"）；最多 16 MiB，**不论总大小都切成 16 块**依次读入。

### 4.4 计算阵列 【HAT】【计时】

- HAT[0x238] = 8 个计算组，但 ioreg 登记的是 16 个核，两者怎么对应不知道。
- FP16：乘法用 fp16 输入，累加位宽高于 fp16（具体多少没测），输出舍入成 fp16。
- **输出通道组（OCG）**：一次通过累加器能算出多少个输出通道。OCG = min(2 的幂次的累加器预算, 按权重格式定的字节上限 32/16/8 B)。
  - 字节上限在 HAT[0x388–0x398]；
  - 每个累加器的档位在 HAT[0x3a8–0x3c0]。
- 文末说明：HAT 里的 8/4/2/1 描述的是累加器分块，**每周期的通道宽度和时钟频率都没测出来**。

### 4.5 DMA 【HWX 对比】【计时】

- 程序里引用了 3 个 tile DMA 和 1 个 kernel DMA；物理上有几个、队列多深不知道。
- 独立输入平面从 2 个扫到 8 个，每多一个慢约 995 µs，呈线性。文末他承认：这些平面被拆成了更多 TD，**测到的是编译器的调度，不是 DMA 的宽度**。
- DMA_INTER：融合后不再写回 DRAM 再读出（DMA_STORE + DMA_LOAD），中间结果直接留在片上。matmul+bias+relu 融合后快 5.7 倍，这个数字包含省掉的两次调度开销。

### 4.6 支持的运算 【HWX 修改】【计时】

- 约 50 种硬件层，依据是 `_ANECValidate*Layer` 的导出函数。
- 逐元素运算：256 个 ALU 操作码，由二进制里的**一个操作码字节**控制。
- rsqrt、sqrt、reciprocal 有专用硬件。
- sigmoid、gelu 等：33 个 fp16 采样点存在 `__KERN_0` 段，硬件做线性插值。
  - **验证方法**：把采样点换成 x³（MIL 里没有这个算子），硬件输出正确。
- 不支持的运算（acos、asin、tan、log、cumsum、mod、布尔逻辑）会回退到 CPU（BNNS）或 GPU。

### 4.7 调度 【计时】

- 每次执行约 90 µs，是主机侧 XPC 往返加 IOKit 设置的开销，受 CPU 限制，不随 SoC 功耗状态变化。
- 两个请求并发只省 16%，省的是主机侧的重叠，引擎吞吐并没有翻倍。

### 4.8 性能和 W8A8 【计时】【HWX 修改】

- 功耗口径修正：Part 2、3 的 2.79 W 是在开着低功耗模式时测的。不开低功耗模式时 FP16 是 4.57 W。
- 峰值条件：32–64 层的链，512–1024 通道，空间尺寸 64²–128²。
- 按链深度的吞吐（512 通道，32²）：

| 层数 | FP16 TFLOPS | W8A8 TOPS |
|---|---|---|
| 1 | 5.4 | 5.9 |
| 4 | 9.8 | 12.4 |
| 8 | 12.3 | 18.6 |
| 16 | 11.7 | 22.4 |
| 32 | 16.1 | 27.4 |
| 48（1024 通道，64²） | 18.5 | 36.0 |

- W8A8 每个块的配置字：

| 块 | 模式字 | DMA 字 | 作用 |
|---|---|---|---|
| 第一块 | 0x93418005 | 0x80041240 | fp16 输入，写出 int8 |
| 中间块 | 0xb1418005 | 0x80049240 | 打包 int8 计算，块间每个元素 1 字节 |
| 最后一块 | 0x91418005 | — | 转成输出格式 |

  中间块比 fp16 块多 4 个配置字，包括量化控制和 scale。

- 改字段的实验：

| 改动 | 结果 |
|---|---|
| 只把模式字改成 0x93 | 能执行，但 2,097,152 个输出里有 1,976,199 个不对；耗时从 371.4 µs 变成 703.9 µs |
| 只把 DMA 字改回 0x80041240 | 能加载，执行时返回错误 0x15 |

- 单层卷积（1024 通道，32²）：int8 权重 260.4 µs，fp16 260.5 µs，没有差别。
- 功耗：W8A8 吞吐是 FP16 的 1.95 倍，功耗是 2.7 倍。

### 4.9 形状 【计时】

- 64 通道、128² 的 32 层链：3.92 TFLOPS，只有 1/8 的计算组在忙。
- 经 S2D(4) 变成 1024 通道、32²：16.37 TFLOPS，W8A8 从 6.62 提升到 31.97 TOPS。
- S2D/D2S 本身的开销 0.3–1.4%。**block_size=2 不要用**：编译器会把它变成一个 one-hot 权重的卷积，开销 2.8–3.1%。
- 结论：编译器把输出通道分给各个计算组，所以按输出通道并行。

### 4.10 限制

| 项目 | 结果 |
|---|---|
| 图深度 | 每个张量 128 KiB 时，383 个块能编译、加载、执行；384 个块时 ANECompilerService 断开 |
| 数据格式 | 只有 FP16 和打包 W8A8；H16G 的 E4M3（FP8）能力位是 0 |
| 控制流 | HWX 里只有 DMA、计算、同步、终止四类记录，没有分支或谓词。走哪个子程序在提交前就定了 |

## 5. 他明确说没解决的问题（我们的机会）

1. 程序最大长度：384 是编译器的限制，硬件上限没测到。
2. **内部重叠**：
   - matmul 和一个独立的 relu 放在一起，只省 19.5 µs（1.1%）；
   - 8 个独立 add 比 8 个串联 add 只快 1.0083 倍；
   - 这些都是整图级的计时。**同一个 TD 内 MAC、平面引擎、DMA 之间怎么重叠，没有解决**。
3. **DMA 拓扑**：物理引擎数量和队列深度。
4. **乘加阵列宽度和时钟频率**。
5. **WAIT / WAIT_EXT** 的同步目标、范围和延迟。
6. **M6**：他没有 M6，原话是 "We do not have an M6 to test"。他建议的测试顺序是：先读 HAT，再测单引擎和双引擎的调度，最后做重叠测试。

## 7. 在 M6 上复现的可行性

| 内容 | M6 现状 | 难度 |
|---|---|---|
| 设备身份（ioreg） | 待查：看 M6 上是否有两个设备、架构名、核数 | 低 |
| HAT | `ZinIrHalH18::GetParams` 存在，但没有导出，需要在自己的进程里用 LLDB 定位 | 低到中 |
| HWX 对比 | 先要拿到 HWX：可能在 aned 的缓存里，也可能要直接调用 `ANECCompile` | 中 |
| 修改 HWX 后执行 | 需要绕过 aned 直接加载自己的 HWX，他没有公开这部分方法 | 中到高，有整机重启的风险 |
| 计时实验 | 现有工具（anebench、ane_bw）大多能做 | 低 |
| 双引擎 | anemon 能分别看两个引擎的活动，这一点他没有 | 中 |
