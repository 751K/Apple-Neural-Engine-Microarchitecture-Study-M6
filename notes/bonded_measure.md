# M6 双 ANE（bonded）实测

- 日期：2026-10-02，M6（T8152），macOS 27.0.1
- 只用公开接口：Core ML（`MLModel`，`CPUAndNeuralEngine`）跑模型；IOReport（不需要 root）读两个 ANE 各自的中断计数和 DRAM 链路带宽直方图。
- 工具：`tools/common/bondrun.m`（计时 + 每个 ANE 的计数），`tools/08_bonded/bond_sweep.py`（生成模型），`tools/lib/hwx_bonded.py`（看编译产物里有几个 kick）。
- 原始输出：`data/08_bonded/bond_sweep_run1.txt`、`data/08_bonded/bond_calib_run.txt`、`data/08_bonded/bond_wsweep_run.txt`、`data/08_bonded/bond_dsweep_run.txt`、`data/08_bonded/bond_ksweep_run.txt`
- 局限：不能让同一个模型分别走单 ANE 和双 ANE，只能比较编译器阈值两侧形状相近的模型。

## 1. 怎么判断用了哪个 ANE：IOReport 中断计数

`Interrupt Statistics (by index)` 里每个 ANE 有自己的子组（`ane …` 是 ANE0，`ane1 …` 是 ANE1），"First Level Interrupt Handler Count" 是中断次数。校准结果：

| 情况 | ANE0 中断 | ANE1 中断 |
|---|---|---|
| 空闲 0.5 s | 0 | 0 |
| 编译产物里 bonded 只有 ANE0 一个 kick 的模型（1×64、1×1 卷积） | ≈3.8 次/调用 | **0** |
| bonded 有两个 kick 的模型 | ≈2–3.5 次/调用 | **与 ANE0 相同** |
| 常量权重 matmul（M=1 或 64） | 0 | 0（Core ML 把它放在 CPU 上） |

结论：
- 这个计数器能可靠区分两个 ANE。
- **只要编译产物里有真正分到两个 ANE 的 bonded 版本，Core ML 运行时就选 bonded**；没有的话，单个进程只用 ANE0。多个进程同时提交时，内核会把请求分到 ANE1（见 `scheduling.md`）。
- `PMP / DCS BW` 带宽直方图分辨率太粗（大多落在最低一档），只能当辅助参考。

## 2. 编译器什么时候切到两个 ANE

1×1 卷积链，512 通道，H=1，只改宽度 W（`w1x1_*`）：

| W | bonded 的 kick 数 | 实测 ANE1 中断 |
|---|---|---|
| 64、128 | 1 | 0 |
| 256 及以上 | 2 | 有 |

- 阈值在 W=128 和 256 之间。
- 之前的说法"只沿 H 切"不对：H=1 时会**沿 W 切**。W=256 的 TD 里两个 ANE 的宽度字段都是 0x80，即各算 128 列。
- 1×4096、2×2048、…、64×64（同样 4096 个像素）全部都切到两个 ANE。

### 2.1 决策机制（逆向 + 编译产物，2026-10-03）

- **两套程序**：每个 h18g 的 HWX 都同时含 nonbonded（单 ANE）和 bonded（双 ANE）两套程序。在 bonded 程序里，编译器再决定每个子图是**拆到两个 ANE 上**，还是**全部留在 ANE0**（此时 bonded 程序没有 ANE1 的指令流，运行时只用一个 ANE）。所以"用一个还是两个 ANE"是编译期决定的。
- **决策者**：空间切分步骤（`ZinMirSpatialSplitter`、`BondedSplitSubgraphIdentification`）。它找出可切的子图，用 `ClusterSplitCostModel::FindOptimalSplit / EvaluateCandidateCost` 评估候选切法，用 `LatencyInfo::ComputeSplitLatencyBonded`、`IsCurrentGraphMinLatencyInBonded` 比较延迟，取延迟最小的方案；没有候选比不切更快时就不切。相关开关：`EnableForcedMaximalBondedSplit`、`DisableBondedNetworks`、`ForceAllToANE0OnBondedProcedure`（`ANECCompile` flags 字典键）。
- **观察手段**：`anecc` 加 `DumpFusionBoundaryInfo=true` 会输出各阶段的图（`*.zinir_graph_final_fusion_info_main__bonded.json`），节点带 `AneIndex`、`PieceID`，节点名里有变换链（`ss_tile_xfm` = 空间切块，`kss_stream_xfm` = 权重分趟流式读入，`concat_sssg_xfm` = 合并）；再用 `tools/lib/tdwalk.py` 读每个 ANE 的 TD 形状。全部 288 个形状（256 通道，4×32 / 8×32 / 16×32，2–24 层）的结果：`data/08_bonded/bsdecide.txt`（`tools/08_bonded/bsdecide.py`：nonbonded 程序 `exe_cycles` 之和、bonded 是否有 ANE1 流）。
- **两种切法**（`tools/lib/tdwalk.py` 读每个 ANE 的 TD）：

| 切法 | 条件 | 例子 |
|---|---|---|
| **按行（空间）** | 整条链融合成"切块"，每个 ANE 在自己那一块上跑完所有层，最后 CONCAT；竖向核需要带上重叠行（halo），层越多重叠越多 | 8×32 的 1×1–1×8：每个 ANE 4 行；16×32 的 3×1：每个 ANE 输入 9–10 行、输出 8–9 行；16×32 的 1×9：每个 ANE 8 行（两边各读一份完整权重，见 B4c 第 8 点） |
| **按输出通道** | 把单 ANE 时已有的"权重分趟"（每个 NE 权重超过 64 KiB 时按输出通道分成的几趟）分给两个 ANE；只在各趟大小相同时发生 | 8×32 的 13×1、15×1：单 ANE 每层 2 趟 × 128 通道 → 每个 ANE 1 趟；5×5：4 趟 × 64 → 每个 ANE 2 趟；16×32 的 1×12–1×14 |

- **不切的情况**（8×32，到 24 层都不切）：
  - 1×9–1×15：权重在一个 TD 内流式读入（每层 1 个 TD、256 通道），没有可分的"趟"；按行切又不会更快（读权重受限）。
  - 3×3、9×1：两趟是 32 + 224 通道，极不均匀，不能按通道切；只有 8 行，按行切要带 halo，不划算。11×1：两趟 96 + 160，同样不切。
  - 3×1–7×1：每 NE 权重 ≤ 64 KiB，只有一趟；按行切要带 halo。
  - 4×32：所有形状都不切（每个 ANE 只能分到 2 行）。
- **门槛**：8×32 的 1×2–1×8 按行切时，有一个相当干净的阈值——按 nonbonded 程序各 TD 的 `exe_cycles`（编译器自己的延迟估计，hwx_h18g.md §11.4）求和，≤ 44 时不切，≥ 48 时切（1×4：4 层 24 不切、8 层 48 切；1×7：4 层 44 不切、8 层 88 切；1×8：3 层 39 不切、4 层 52 切）。1×1 在 16 层（和为 17）就切，是因为 1×1 链中多数层从 L2 链式读入，`exe_cycles` 记为 0，和被严重低估。推测：切分有固定开销（两边同步、最后合并），估计延迟要超过约 45 个单位，省下的时间才够抵消。
- **16×32 起几乎都切**（每个 ANE 能分到 8 行）；唯一例外是 1×9 的 4 层。
- 评价：成本模型没有考虑"两个 ANE 共享读权重带宽"。所以对读权重受限的层，它在 16×32 上仍选择按行切（两边各读一份权重），结果没有加速（defects.md B9）；同一层在 8×32 上不切反而是对的。

### 2.2 成本模型的公式（逆向，2026-10-03）

- **决策公式**（反汇编 `ZinMirSpatialSplitter::IsCurrentGraphMinLatencyInBonded`、`LatencyInfo::ComputeSplitLatencyBonded`）：

  ```
  切分后延迟 = ( Σ_层 切分后各块的计算延迟 + Σ_层 输入拷贝 / 合并延迟 ) × 0.5
  切   ⇔   Σ_层 切分前延迟 > 切分后延迟   且   不比"进一步细分"差（HasLessLatencyThanFurtherSplitGraph）
  ```
  - 三项都是按层存的 `map<层, double>`（`SubgraphSplitInfo` +0x150 切分前、+0x168 切分后各块、+0x1b0 拷贝 / 合并），逐项求和。
  - **× 0.5 就是"两个 ANE 完全并行、互不影响"的假设**：没有任何项考虑两个 ANE 争用同一份 DRAM 带宽。若对象上的"强制最大切分"标志（`EnableForcedMaximalBondedSplit`）置位，直接返回"切"。
- **数值验证**：TD 头的 `exe_cycles` 就是同一个性能模型的逐层延迟估计。nonbonded 程序各 TD 之和 = 切分前；加 `EnableForcedMaximalBondedSplit=true` 编译得到的 bonded 程序各 TD 之和 = 切分后各块；于是"增益 = 2 × 切分前 − 切分后各块"，与是否切分对照即可反推出"拷贝 / 合并"一项（`data/` 中的 `bsdec/ch`、`bsdec/forced` 产物在 M6 上，分析脚本 `tools/08_bonded/bs_split.py`、`bs_split2.py`、`bs_split3.py`、`bs_io.py`（在 M6 的 ~/anehal/hwx 下运行））：

| 情况 | 反推的"拷贝 / 合并"开销 | 依据 |
|---|---|---|
| 8×32、256 通道（128 KiB）按行切，1×2–1×8 | **44 < 开销 ≤ 46**（各核一致） | 1×7 的 4 层增益 44 不切，1×4 的 8 层增益 46 切 |
| 4×64、256 通道（128 KiB） | 34 < 开销 ≤ 46 | 与 8×32 一致：取决于字节数，不是形状 |
| 9×32 及以上、或宽 33–72（行补齐到 128 B，实际 ≥ 144 KiB） | < 6–17（1 层即切） | 9 行起；宽 33 时每行补齐到 128 字节，实际 256 KiB |
| 512 通道（按输出通道切） | ≈ 0 | 把已有的两趟权重各给一个 ANE，不需要拷贝 / 合并 |
| 竖向核（3×1、9×1、3×3）在 8×32 | 强制切分的增益恒为 2 或 12，不随层数增长 | 按行切的块要带 halo，切了也省不下时间 |

- **补充实验：开销取决于"每块像素数"，不是张量字节数**（`tools/08_bonded/bs_split3.py` 及通道扫描；用户提出"会不会是每 NE 64 KiB × 2 = 128 KiB"，据此设计）：

| 模型（1×4 链） | 激活 | 每 NE 权重 | 切后每块 | 每块像素 | 反推开销 |
|---|---|---|---|---|---|
| 8×32，160 / 192 / 224 / 256 / 288 / 320 / 384 通道 | 80–192 KiB | 12–72 KiB | 4 × 32 | **128** | (24, 32] / (28, 44] / (46, 70] / (40, 46] / (30, 62] / (38, 78] / (52, 108]，约与通道数成正比 |
| 4×64，256 通道 | 128 KiB | 32 KiB | 2 × 64 | **128** | (34, 46] |
| 8×33，256 通道 | 132 KiB | 32 KiB | 4 × 33 | 132 | < 6 |
| 9×32，256 通道 | 144 KiB | 32 KiB | 5×32 / 4×32 | 160 / 128 | < 8 |
| 8×64，128 通道 | **128 KiB** | 8 KiB | 4 × 64 | 256 | ≤ 8 |
| 8×64 / 16×32，256 通道 | 256 KiB | 32 KiB | 4×64 / 8×32 | 256 | < 14 |
| 8×32，512 通道 | 256 KiB | 128 KiB | 按通道切 | — | ≈ 0 |

- 结论：
  1. **"约 45"是成本模型给"按行切 + 合并"算的拷贝开销，只在切后每一块都 ≤ 128 像素时出现**，大小约与张量字节数成正比（约 0.35 单位 / KiB：160 通道约 30、256 通道约 45、384 通道约 70）；只要有一块超过 128 像素（4×33、5×32、4×64），开销就几乎为零，1–2 层即切。
  2. 已排除的解释：①"合并张量是否命中系统缓存"（`IsMcacheReadHitConcatTensor`）——阈值在 bonded 模式下取自 SoC 参数的 MCache 大小（参数链 ZinIrParameters → HAL → SoC 参数对象 → 数据块 +0 = 16 MiB），远大于这些张量；② 子图"输入 + 输出 ≤ 256 KiB（HAL L2 驻留阈值）"——只改输入 / 输出通道（72–288 KiB）时都在 2 层就切（`tools/common/ioch.py`）；③ 激活 ≤ 128 KiB——128 通道 8×64 也是 128 KiB 却没有开销；④ 每 NE 64 KiB 权重缓冲 × 2——256 通道 1×4 每 NE 权重只有 32 KiB，而 160 通道（12 KiB）同样有开销；⑤ small source mode——切后各块任务信息字中该字段均为 0。
  3. 128 像素对应的代码位置（性能模型中哪一项拷贝延迟以"每块 ≤ 128 像素"为条件）未定位。128 像素正好是之前测到的"单 ANE 计算与读权重平衡点"（4×32），以及按行计时时 32 列的窗口 × 4 行，是否相关未证实。
  3. **B9（读权重受限的层按行切分不加速）的根本原因**：`ComputeSplitLatencyBonded` 直接把总延迟 × 0.5，默认两个 ANE 各自拥有完整的读权重带宽；而实际两个 ANE 共享约 150 GB/s。按行切时两边各读一份权重，成本模型以为快了一倍，实际一点没快。
  4. 4×32 不切、8×32 的 1×9–1×15 不切等，都是同一公式的结果：要么切后每块太小（增益被拷贝开销吃掉），要么没有可用的切法（权重流式读入没有"趟"可分、两趟不均、竖向核的 halo）。

## 3. 双 ANE 能快多少

### 3.1 方法

每次调用都有一两百微秒的固定开销（Core ML + 驱动），而且层数少时开销和计算会重叠。所以不看单个模型的吞吐，而是**固定形状、改层数，用耗时对层数的斜率算出每层的边际成本**。

对比的两组：
- W=128：单 ANE，每层 67.1 MFLOP。
- W=256：双 ANE，每个 ANE 正好算 128 列，和单 ANE 那组每个引擎的工作量完全一样。每层共 134.2 MFLOP。

每组都测两种权重：
- 共享权重（`k1x1_*`）：所有层用同一个 const，HWX 只有 688 KB，权重留在片上。
- 独立权重（`d1x1_*`）：每层权重不同，L=128 时共 64 MB，必须从 DRAM 读。

每个点调用 600–1000 次取中位数，测两轮。两轮的差别小于 1%。

### 3.2 结果（共享权重，中位数耗时 µs）

| 层数 L | 单 ANE W=128 | 双 ANE W=256 |
|---|---|---|
| 16 | 229 | 227 |
| 48 | 330 | 388 |
| 128 | 718 | 806 |
| 256 | 1178 | 1234 |
| 384 | 1595 | 1669 |

L=256→384 的边际成本（最线性的一段）：

| | 每层耗时 | 边际吞吐（fp16） |
|---|---|---|
| 单 ANE | 3.26 µs | **≈20.6 TFLOPS** |
| 双 ANE | 3.40 µs | **≈39.5 TFLOPS** |
| 比值 | | **1.92×** |

- 双 ANE 每层多 0.14 µs（约 4%），是两组模型边际耗时之差（额外协同时间），推测主要是同步，但没有和资源竞争等因素分开；不能当作需要交换数据的运算的开销下限（2026-10-05 补）。
- 换算下来，单个 ANE（16 个 NE）fp16 约 20 TFLOPS，两个 ANE 合计约 40 TFLOPS。
- 整个模型的吞吐（含固定开销）最高测到 30.9 TFLOPS（W=256，L=384）。
- 层数少时斜率不稳定：单 ANE 在 L=16→48 只有 3.15 µs/层，L=48→128 则是 4.85 µs/层。原因未确定，可能是开销重叠，或者编译器对长链的分段方式不同。

### 3.3 独立权重：bonded 时两个 ANE 各读一份权重

| L=48→128 每层边际耗时 | 共享权重 | 独立权重 |
|---|---|---|
| 单 ANE W=128 | 4.85 µs | 5.1 µs（几乎不变） |
| 双 ANE W=256 | 5.2 µs | **7.3 µs** |

- 单 ANE 每层读 0.5 MB 权重，0.5 MB / 5.1 µs ≈ 100 GB/s，还没碰到带宽上限。
- 双 ANE 时，编译产物把同一份权重分别映射给两个 ANE，每个 ANE 都要读完整的权重：2 × 0.5 MB / 7.3 µs ≈ **140 GB/s**，接近 DRAM 带宽，所以变慢。
- 结果：权重放不进片上内存时，双 ANE 的收益从 1.9× 降到约 1.4×（同样计算量下）。**bonded 按空间切分，权重流量翻倍**，所以对权重带宽受限的负载帮助有限。

## 3.4 编译器怎么决定双 ANE 拆分（2026-10-05，反汇编 + lldb；whisper_compile.md §3.4，全文 `private/data/03_compile/spatial_split/spatial_split.md`）

- **只有全局细化路径会做双 ANE 切分**：`ZinMirSpatialSplitter::Tile` 在 `GlobalRefinementInSpatialSplit` 打开（默认）时走 `TileWithGlobalRefinement`；
  关掉时走旧路径，只用单引擎判据 `IsWorthTile`，一刀都不切，bonded 程序退化为全部在 ANE0（Whisper 实验中"关掉全局细化后只剩 ANE0"的原因）。
  进入前还要求 procedure 是 bonded 且 HAL +0x73c 置位（2026BaseLine 为 1）。
- **怎么切**：每个子图只沿一个维度切（H = 1 的张量沿 W，64×64 沿 H）；BondedSplit 恒切 2 块；切点对齐到 256 B（FP16 为 128 列，W 太小时 64 列），
  第 0 块 = ⌈W/2⌉ 向上取整到 128（剩余不足 128 时向下取整），例如 W = 300 → 128 | 172、375 → 128 | 247、384 → 256 | 128、640 → 384 | 256。
- **分给哪个 ANE**：子图所有层的 `AneIndexHint` 相同时整个给那个 ANE；否则第 i 块给 ANE `(i ≥ T/2)`——**块数为奇数时多出的一块给 ANE1**（defects B8 的机制）。
- **切不切**：`IsCurrentGraphMinLatencyInBonded`：`切前延迟 > 0.5 × (各块延迟之和 + 拷贝开销)` 且不如进一步细分（延迟单位 ms，来自 perfmodel 的 NE 光栅化估计）。
  **没有不均衡项**，等于假设两块一样大、两个 ANE 互不干扰。实例（512 通道 1×1 链，16 层，H = 1）：W = 128 时切前 0.0550、切后 0.1022 → 不切（单 ANE）；
  W = 256 时 0.10454 对 0.10374，**只赢 0.8%** 就切成双 ANE——这就是 §2 宽度扫描里 W = 128 / 256 的阈值。
- **细化怎么进行**：子图工作表；整体切更好就定稿，否则按候选切点（`ClusterSplitCostModel::FindOptimalSplit`）细分后放回工作表，直到表空。
  另有编译时间闸门 `IsWorthCompileTimeIncrease`（增益 < 2% 且 层数 × 块数 > 3 × 946 时放弃）。

## 4. 其他观察

- 每次调用的中断数随单次工作量变大而减少（W=64 时约 3.8 次，W=4096 时约 2.25 次）。可能有一部分中断和数据量有关（例如 DMA 分块），没细查。
- p90 经常是中位数的 2–3 倍，说明 Core ML 调用的延迟有长尾（可能是 DVFS 或调度），所以文中都用中位数。
- 第一轮里同样是 4096 像素的 1×1 链（L=8）测到 1.5 ms，比后来 L=16 的 1.23 ms 还慢。这个结果没有复现，当作噪声。
