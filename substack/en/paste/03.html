Apple M6 ANE Microarchitecture, Ch. 5 (Part 2): Compiler and Program Format

This post is chapter 5 of the report "Microarchitecture of the Apple M6 Neural Engine: An Empirical Study Based on Compiled Artifacts, Execution Traces, and Power Measurements", reproduced unchanged. Full report: web; data and tools: GitHub. Section, figure and table numbers follow the report.

5.7 Format of the Task Descriptor

maderix [1] observed that the compiled artifacts store configuration parameters rather than instructions. The analysis in this report further shows that a TD is in effect a sequence of register-write packets. Each TD sequence begins with a sequence header of four words (values 1, 0, 0, 0). Each TD begins with a 12-word task header, followed by several write packets, each consisting of a packet header and data, and ends with several address packets. Figure 5-2 illustrates this structure. The following subsections discuss, in order, the task header, the encoding of write packets, the grouping of registers, the convolution configuration word, the opcodes of elementwise operations, address packets, and the layout version.

Figure 5-2. Structure of a TD (v24 layout). At the top is the TD sequence of one ANE. Below it, one TD is expanded: ① the task header, ② the write packets arranged by register group, and ③ the address packets at the end. The register groups of the write packets are arranged in the direction of data flow. ④ gives the bit format of the packet header words, illustrated by three header words from ② and ③. The example is taken from the artifact of a 1×9 convolution with 256 channels, an 8×32 input, and four layers on h18g.

5.7.1 Task Header

The compiler's assertion strings refer to the 12 words of the task header as td_header0 through td_header11. We disassembled the field-reading function for the v24 layout (ZinGetRegisterProgramming<24>) and the functions that write the task header (HandleTdHeader, SetEventFlags, and others), and we compared them with the actual values in the artifacts. This yielded the field meanings listed in Table 5-6 〔compiler, HWX〕.

Table 5-6. TD task header (v24)

Two fields are analyzed further in later sections. The first is the exe_cycles field, which is written by the function CalculateExeCycles in units of about 1 µs. For example, the values for the three TDs of a 1×9 convolution with 256 channels on a 16×32 input are 7, 11, and 11, which are proportional to the output channel counts 64, 96, and 96. The value for a 1×1 FP16 convolution TD agrees with the time obtained by converting at 20.6 TFLOPS. For dense layers, exe_cycles agrees with the per-TD estimates of the compiler's performance model. For pruned sparse layers, it does not agree, and the algorithm responsible has not been determined in this report (Section 7.8). The second is the three groups of event masks, which determine at which moments during TD execution the firmware records which events. Because the masks of the first and last TDs differ from those of the other TDs, we can obtain the task-start and task-end timestamps of each invocation from kdebug traces. Chapter 6 uses these timestamps to decompose the time of each invocation, and Chapter 11 uses them to infer clock frequency 〔compiler, HWX〕.

5.7.2 Encoding of Write Packets

The content after the task header consists of three kinds of packets, whose encodings are shown in Table 5-7 〔HWX, compiler〕.

Table 5-7. The three kinds of packets in a TD

The word immediately after the input-channel count in a convolution TD is the masked-write packet header. Its value varies with the model. Most convolutions, such as 1×1 and 1×3, have 0x91498005; 1×8 convolutions and dilated convolutions have 0x93498005; and 3×3 convolutions in W8A8 mode have 0xb3498005 (samples: xword_samples.txt). Decoded according to the masked-write format, 0x91498005 denotes base register 5 (Wout) and mask 0x2293, and it writes seven registers in order: Wout, Hout, Cout, the convolution configuration word, TileHeight, the task information word, and register 19. It follows that this word is not a register value; it is a packet header generated during serialization according to which fields must be written. The differences between models can be explained on this basis. In W8A8 mode, one additional register must be written (base + 15, that is, register 20), so the mask gains one more bit, corresponding to bit 29. When the same layer is split into several TDs, register 16 is written in some TDs and omitted in others, so the bit corresponding to bit 25 in the mask varies from TD to TD 〔HWX, compiler〕. The TD parsing tool is tdpkt.py.

5.7.3 Register Groups and the Pipeline

For each TD layout version, the compiler defines a class ZinAneTdHw_vN. Field-reading functions are named ZinGetRegisterProgramming<N>::GetXxx, and each function reads one word at a certain offset of the TD object and extracts several bits. We disassembled all of the reading functions and obtained the offset and bit width of each field (summary: td_field_offsets.txt). Arranged by offset, the groups of fields appear in the order shown in Table 5-8 〔compiler〕.

Table 5-8. Order of the field groups in a TD (by object offset in v31 and v36)

This order is consistent with the direction of data flow in the hardware. Data is read from DRAM by the input Tile DMA, enters the NE and PE through L2, and is written back to DRAM by the output Tile DMA. It also agrees with the data flow that Bryngelson [5] derived from the M1 register groups (DRAM → L2 → NE → L2 → PE → DRAM). The NE field group contains an accumulator bias-shift field and a 5-bit output right-shift field, which are the configuration required by fixed-point accumulators: accumulation takes place in a fixed-point format, and the output is right-shifted and converted to FP16. Chapter 8 directly measures the accumulator as a Q15.16 fixed-point format with constructed inputs, which is consistent with these fields. The DoubleRate fields of the input Tile DMA and the L2 DMA have existed since v24. The CanEnableDoubleRateMode switch in the parameter table (offset 0x5f7) should be the condition for enabling these fields; it is 0 in H18 and 1 in 2026BaseLine, which M6 uses, and in H19. Nevertheless, neither the FP16 nor the INT8 models used in this report triggered double-rate mode 〔compiler, HAL, inferred〕.

5.7.4 Convolution Configuration Word

The geometry of a convolution is encoded together in a 32-bit configuration word (offset 0x2a0 in the compiler's object; register 10). We disassembled the 13 functions that write this word (ZinAneTd<31>::SetCommonConvCfg*, and others) and obtained the bit definitions listed in Table 5-9. The parameters of a three-dimensional convolution have a second configuration word (offset 0x2a4), in which Kd occupies bits 0–4, Sz bits 6–7, Pz bits 8–11, and Oz bits 13–14 〔compiler〕.

Table 5-9. Bit definitions of the convolution configuration word

For example, the configuration word of a 1×3 convolution is 0x5002a043, which decodes to Kw = 3, Kh = 1, Sx = 1, Sy = 1, PadLeft = 1, Ox = 1, and Oy = 1. The configuration word of a 3×3 convolution is 0x5042a0c3. In all compiled artifacts, bits 12 and 27 are 0, and the functions that write this word do not modify these bits, so they are reserved. Ox and Oy denote the number of output pixels produced per input stride. Field tracing (Section 5.7.8) shows that Ox and Oy are 2 for transposed convolutions and upsampling, which are implemented as an ordinary convolution with interleaved output, writing every other position 〔compiler, HWX〕. Although the kernel-width field has 6 bits, the largest kernel width that the compiler encodes directly with stride 1 is 8. For kernel widths of 9–15, the compiler rewrites the convolution in the form Sx = 2 and Ox = 2, sets the output-width field to half the actual width, and stores the weights as two sets of kernels offset by one position. Section 7.4.1 compares the configuration words and weight volumes for different kernel widths and gives the full justification for this rewriting rule (data: convcfg_scan.txt; tool: convcfg.py) 〔compiler, HWX〕.

5.7.5 Opcodes of Elementwise Operations

maderix [4] reports that ALU operations are controlled by an opcode byte, with 256 possible values. To confirm the encoding of opcodes on the M6, we compiled a fused layer consisting of a 1×1 convolution followed by a two-input elementwise operation, using five operations: addition, subtraction, multiplication, maximum, and minimum. The TD sequences of the five artifacts have the same length (0x294 bytes), and they differ in substance only in a single word at offset 0x240 within the sequence, as shown in Table 5-10 〔HWX〕.

Table 5-10. Encoding of elementwise operations

Table 5-10 shows that, in this fused layer, the operation type is encoded in a 2-bit field (0 for addition, 1 for multiplication, 2 for maximum, and 3 for minimum), and subtraction is implemented as addition with the second input negated (bit 18). The TD sequence of division (real_div) is longer (0x338 bytes). We speculate that it is split into two steps, a reciprocal (computed with a lookup table and interval reduction) and a multiplication 〔HWX, inferred〕. This experiment covers only this one type of fused layer. Other layer types may use more encodings, so the results of this report do not contradict the 256 opcodes described by maderix.

5.7.6 Address Packets and BARs

Address packets are located at the end of each TD. Each address packet writes an offset within a buffer into a base register, and its BAR number indicates which buffer the offset is relative to. We counted more than 1600 address packets and found that they write only five groups of registers (tool: hwxreloc.py). To determine the buffer corresponding to each register group, we constructed a model with two inputs and two outputs: o1 = relu(conv(x) + y), o2 = relu(conv(y)) (generation script: io2.py; artifacts: l2hwx/io2). Table 5-11 gives the results of the analysis 〔HWX, compiler〕.

Table 5-11. Registers written by address packets and their BAR numbers

From Table 5-11, the BAR numbering rule can be summarized as follows. Slot 4 is for weights, and slot 20 is for DSID parameters. Slots starting from 24 are assigned to the tensors in sequence, outputs first and then inputs, with four slots for each tensor. All 64-bit address packets use even BAR numbers, which is consistent with the assertion string in the compiler, "64-bit relocation, BarIdx must be even". The base address of the weights is determined at load time through static relocation. The base addresses of inputs and outputs have no relocation entries; instead, the runtime fills them in on each invocation according to the BAR number, and mapping entries such as x and o1@output in the __RUNTIME segment describe this correspondence. The values in address packets are offsets within buffers. For example, in a dual-ANE program, the offset carried by the input address packet of ANE1 points to row 32 (Section 5.8.1). In the artifacts of h18 (v20 layout), the same register uses a different BAR number (for example, 28 for weights), which shows that the BAR layout varies across versions 〔HWX〕.

5.7.7 Layout Versions

The register layout of the TD changes with the architecture. We determined the layout version for each target along the following path. The constructor of ZinAneTd<N> is inlined into the function CodegenCreateInstructions<N>. The sole caller of the latter, arch_dispatch<CodegenCreateInstructionsDispatcher>, uses AneArchEnum − 1 as an index into a 36-entry jump table, in which entry N jumps to CodegenCreateInstructions<N>. It follows that the template parameter N is the value of AneArchEnum. AneArchEnum is in turn obtained from the CPU subtype of the HWX by the function ZinCpuSubtypeToArchValue (tools: adrref.c, jtab.c, tblread.c). Table 5-12 lists the relevant part of the lookup results 〔compiler〕.

Table 5-12. Correspondence between CPU subtype and TD layout version

To verify Table 5-12, we compiled the same model (256-channel 1×9 convolution, 8×32 input, four layers) to all available targets and compared the register addresses written by each target (data: data/03_compile/tdv/). The results show that changes in register layout correspond one-to-one with changes in the version number. v17 and v19, relative to v8, changed the DMA register groups. v20, relative to v19, inserted two registers in the register groups related to L2. v24, relative to v20, inserted one register after the first NE register; the write addresses of the NE group change from 0x1240, 0x1241, and 0x1244 to 0x1240, 0x1242, and 0x1245. The TD sequences of h18g and h19 are almost identical word for word. They total 17948 bytes, and the differences are confined to one field in the task header and one command word at the end of a TD. In addition, the positions and bit definitions of the shape fields, the convolution configuration word, TileHeight, TileOverlap, and the task information word are exactly the same in v19, v20, v24, and v31. Therefore, the decoding results for the v31 functions in Section 5.7.4 also apply to the M6 〔compiler, HWX〕.

Of the four layout versions in Table 5-12 with numbers larger than v24, v26 corresponds to the target named M12 internally by the compiler, which should not be confused with the M-series chips. Its ArchCompareValue is the same as that of v24, so v26 is more likely a variant of the same architecture generation on another product line. v28, v31, and v36 are the architectures newer than the M6, and Section 15.3 discusses the fields they add 〔compiler, inferred〕. The lookup results of this report differ from Bryngelson [5] in two places. First, Bryngelson records the layout of the M1 as v10, whereas the lookup in this report gives v7 for H13 (M1). In this version of the compiler, v10 belongs to target M11, whose ArchCompareValue equals that of v8 for H15. Second, Bryngelson states that the M5 uses the v20 layout, whereas the lookup in this report gives v19 for H17 (the M5 generation) and v20 for h18. Both differences may arise from different compiler versions, because the layout version number is an internal template parameter of the compiler, and different compiler versions may assign different numbers to the same architecture. Without the corresponding compiler version and device, this report does not verify this further. Chapter 15's comparison table uniformly adopts the lookup results of this report and notes the notation used in the literature.

5.7.8 Dynamic Tracing of Fields

By tracing the calls to field functions dynamically, we can further understand how each field is actually read and assigned. On the M4, we compiled a batch of small models for h18g with the same version of the compiler. We used lldb to set breakpoints in the 403 field-setting functions of the TD class ZinAneTd<24> for the v24 layout. We recorded the arguments and callers of each call, as well as the changes in register values in the TD object before and after each call (Section 3.2; tools: tdtrace_gen.py, tdtrace_lldb.py, tdtrace.sh, tdtrace_fit.py) 〔compiler〕. The correspondence between register addresses and object offsets was taken from the disassembly of ZinAneTdHw_v24::GetRegisterValueFromAddress. The first batch of 35 models covers various convolution kernels, strides, dilation, grouping, transposed convolutions, activation functions, normalization, sparse and quantized weights, matrix multiplication, elementwise operations, pooling, reductions, softmax, concatenation, transposition, padding, upsampling, and dual-ANE programs. Across these models, 226 setter functions were called 47508 times in total. The register values reconstructed from the trace agree with the actual values in the HWX in 89% of cases. The disagreements are concentrated in address-type registers, which are rewritten by address allocation and relocation after TD generation. We then extracted from the disassembly the bits that each setter clears and sets (tdstatic.py), and merged them with the trace results and the actual HWX values on a "register → bit field" basis (tdmanual.py). This yielded 312 bit fields: 104 vary with the model, 86 are constant, and 122 do not appear in this batch of models. For these 122 bit fields, we designed a second batch of 32 models by field name, and we added several variants with compilation options. This reduced the number of bit fields that do not appear to 79 〔compiler, HWX〕. Because this field table is derived from the compiler, this report provides only field names and value patterns, and it does not distribute the field table itself. Table 5-13 lists the fields relevant to other sections of this report.

Table 5-13. Selected fields determined by dynamic tracing (v24 layout)

The second batch of models also revealed several hardware functions not treated in other sections of this report 〔compiler, inferred〕. Gather-type operations (gather, gather along an axis, and embedding) write the entire group of texture fields (0x1372–0x137a, TextureMode = 1), indicating that the ANE's gather borrows the texture sampling unit. This corresponds to the "accelerated texture sampling" switch newly added to the 2026BaseLine parameter table (Section 15.3). A group of fields named RCAS (0x1246) appears only in topk. Combined with strings such as rcas_kernel and ne_supports_rcas in the compiler, we speculate that it is a comparison-and-selection unit inside the NE. Large mirror (reflect) padding is implemented with circular-addressing fields (0x1059–0x105a). 3D convolutions use the depth-dimension shape fields and the three-dimensional configuration word described in Section 5.7.4, and they are natively supported operations. The compiler option ForcePerfTracerRegisters writes seven groups of performance-tracing configuration for L2, PE, NE, Tile DMA source and destination, and weight DMA, indicating that the hardware has per-unit performance counters. Under the constraints of this report, however, these counters cannot be read (Section 16.1).

The 79 bit fields that still do not appear are mostly features that this version of the compiler does not use by default on h18g: activation compression (about 30 bit fields, which the compilation option EnableIntermediateCompression also fails to make appear), weight coefficient DMA (about 12), multiple palettes (5), static circular addressing and index addressing for L2 and PE (about 15), and TileOverlap and stochastic rounding (StochasticRound). In other words, the TD layout reserves fields for these features, but neither the existing compiler nor the coremltools models use them. This agrees with the observation in Section 15.3 that a capability opened in the parameter table is not necessarily used 〔compiler, inferred〕.

5.8 Dual-ANE Programs

This section examines three properties of dual-ANE programs: how the TD sequences of the two ANEs differ from those of a single-ANE program; how the two ANEs share data and synchronize when data must be exchanged; and what the compiler relies on to decide whether to split. This section discusses only the compiler's decisions. How the runtime selects between the two programs is described in Section 6.3.2, and the speedup actually achieved by splitting is described in Chapter 10.

Figure 5-3 summarizes the main content of this section.

Figure 5-3. Splitting, synchronization, and the split decision for dual-ANE programs. ① Split by rows: the two ANEs each process half of the rows and each read a complete copy of the weights (Section 5.8.1). ② Split by output channel: the passes already present in the single-ANE program are divided evenly between the two ANEs (Section 5.8.3). ③ When data must be exchanged, the two ANEs map the same shared scratch buffer, and sync records are inserted before the corresponding layers (Section 5.8.2). ④ The compiler compares latency estimates before and after splitting to decide whether to split; the factor × 0.5 assumes that the two ANEs do not interfere with each other (Section 5.8.3).

5.8.1 Differences at the TD Level

For the baseline model, the single-ANE program and each of the two TD sequences of the dual-ANE program contain three TDs, with about 0x4ac bytes per sequence. A word-by-word comparison of the three sequences yields the differences listed in Table 5-14 〔HWX〕.

Table 5-14. Differences between the TDs of the single-ANE and dual-ANE programs for the baseline model

As Table 5-14 shows, for this pointwise convolution chain, the dual-ANE program splits the tensor into upper and lower halves along height. ANE0 computes rows 0–31, and ANE1 computes rows 32–63. Both use the same weights, and each uses all 16 NEs. Each row of a pointwise convolution depends only on the same row of the input, so no data needs to be exchanged between the two ANEs, and accordingly the TD sequences contain no cross-ANE sync records 〔HWX〕.

5.8.2 Shared Scratch Buffer and Sync Records

To study cases that require exchanging data, we compiled four use cases: a three-layer 64-channel 1×1 convolution, a three-layer 64-channel 3×3 convolution, a reduce_sum along height, and a softmax along width (generation script: bonded_cases.py; summary tool: hwx_bonded.py; artifacts: hwx_cases/). Except for the 1×1 convolution, the dual-ANE procedures of the other three use cases contain three additional classes of runtime operations. rt_op_alloc_bss_for_ane16383_P_main__bonded allocates a scratch buffer, where 16383 (0x3fff) should be a mask denoting all ANEs. rt_op_map_shared_bss__ane0 and __ane1 map this buffer to the two ANEs, respectively. rt_param_main__bonded_ane_{0,1}_hi_replaceable_dsid_usage_dsid_relocation supplies each ANE with a DSID relocation parameter. Because the DSID is a tag that the SoC's system-level cache assigns to data flows, and because the compiler contains a symbol named McacheHiBondedKernelReadDSID, we infer that data exchange between the two ANEs is related to the system-level cache 〔HWX, inferred〕. Whether a dedicated channel also exists, and the specific role of the DSID in the exchange, cannot be determined in this report (Section 16.2). In the reduce-along-height use case, the input and output are mapped only to ANE0. ANE1 maps only the shared scratch buffer and its own TD sequence; that is, ANE1 computes the partial sums for half of the tensor and writes them to the shared scratch buffer, and ANE0 performs the final merge.

In the TD sequences of these use cases, we counted the words whose top four bits are 0xf. ffc01540 appears at a fixed position in every convolution TD and is a fixed field of the TD. f0003211 appears at the end of every sequence and exists in both single-ANE and dual-ANE programs, and it should be the stage-end record. f0003281 appears only in dual-ANE sequences that exchange data. Table 5-15 lists the number of occurrences of f0003281 〔HWX〕.

Table 5-15. Number of occurrences of cross-ANE sync records

The number of occurrences of f0003281 agrees with the number of times data must be exchanged between the two ANEs. The words surrounding this record have a fixed format: c0301440 010N00e1 00000400 00010000 f0003281, where N is the sequence number of the sync point, and the low byte 0xe1 marks a cross-ANE sync. The corresponding word in an ordinary end record has low byte 0x21. In ANE1, both kinds of records are followed by two additional words, 00001457 00000020, which we speculate are the semaphore number and count used when ANE1 notifies ANE0. On this basis, we infer that f0003281 is a cross-ANE sync record, corresponding to what maderix [4] and Bryngelson [5] call WAIT_EXT. Because we did not execute a modified program, this conclusion rests only on the position and number of occurrences of this record 〔HWX, inferred〕.

5.8.3 Cost Model for Splitting

When generating dual-ANE programs, the compiler must decide, for each subgraph, whether to split it across the two ANEs or to keep it entirely on ANE0. The spatial-splitting steps (ZinMirSpatialSplitter and BondedSplitSubgraphIdentification) are responsible for this decision. They first identify splittable subgraphs, then use ClusterSplitCostModel::FindOptimalSplit to evaluate candidate splitting schemes, and finally use IsCurrentGraphMinLatencyInBonded to compare latencies before and after splitting. We disassembled the latter and the LatencyInfo::ComputeSplitLatencyBonded it calls, and we obtained the following criterion:

Latency after splitting = (Σ compute latency of each tile after splitting + Σ copy-and-merge latency) × 0.5
Splitting is performed if and only if Σ latency before splitting > latency after splitting, and the split is not worse than further subdivision

In these formulas, all three terms are per-layer estimates from the performance model. They are stored at offsets 0x150, 0x168, and 0x1b0 of the subgraph-split information object, and they are summed by accumulating over layers. The coefficient 0.5 implies that the model assumes the two ANEs run completely in parallel without interference. None of the three terms accounts for contention between the two ANEs for DRAM bandwidth, and none accounts for tiles of unequal size. The criterion considers only the sum of the latencies of the tiles, not the larger of them 〔compiler〕.

To validate this criterion on actual artifacts, we used the exe_cycles values in the TD headers, because these shapes are all dense layers and exe_cycles agrees with the performance-model estimate. The sum of exe_cycles over the TDs of a single-ANE program equals the latency before splitting. When splitting is forced with the option EnableForcedMaximalBondedSplit, the sum of exe_cycles over the TDs of a dual-ANE program equals the compute latency of the tiles after splitting. Combined with whether splitting actually occurred, this allows the range of values of the copy-and-merge latency term to be inferred back. We performed this analysis for 288 shapes with 256 channels; height × width of 4×32, 8×32, and 16×32; and depths from 2 to 24 layers (tool: bsdecide.py; data: bsdecide.txt). The main results are as follows 〔compiler, HWX〕.

On the chain of 8×32, 256 channels, and convolution kernels from 1×2 to 1×8, there is a clear threshold for splitting: a single-ANE program is not split when the sum of exe_cycles is 44 or less, and it is split when the sum reaches 48. For example, for a 1×4 convolution with four layers, the sum is 24 and no splitting occurs; with eight layers, the sum is 48 and splitting occurs. For a 1×7 convolution with four layers, the sum is 44 and no splitting occurs; with eight layers, the sum is 88 and splitting occurs. By back-calculation, the copy-and-merge latency for this class of shapes lies between 44 and 48, about 45. A 1×1 convolution chain is split as early as 16 layers, although the sum of its exe_cycles is only 17. The reason is that most layers of the 1×1 chain are read in a chain from L2, and their exe_cycles are recorded as 0, so the total significantly underestimates the actual latency.

Further experiments show that whether the copy-and-merge latency is counted depends on the number of pixels in each tile after splitting (it is counted only when a tile has no more than 128 pixels). When it is counted, its size is roughly proportional to the number of activation bytes, as shown in Table 5-16 (tools: bs_split3.py, ioch.py) 〔compiler, HWX〕.

Table 5-16. Inferred copy-and-merge latency (1×4 convolution chain)

As Table 5-16 shows, the model counts a substantial copy-and-merge latency only when every tile after splitting has no more than 128 pixels, and its magnitude is about 0.35 units per KiB of activation. As soon as any tile exceeds 128 pixels, this term approaches zero, and chains of one or two layers are split. We excluded the following alternative explanations: whether the merged tensor hits the system cache (the threshold is 16 MiB, far larger than these tensors); whether the sum of the subgraph's inputs and outputs exceeds the 256 KiB L2 residency threshold in the HAL; whether the activations are no larger than 128 KiB; and whether the weights per NE exceed 64 KiB.

The compiler adopts two splitting methods. The first is split by rows. The entire convolution chain is fused into several tiles, each ANE executes all layers on the rows it is responsible for, and the results are finally merged. When the tensor height is 1, the compiler splits along width instead; for example, a 1×256 tensor is split into two 1×128 tensors. The cost of splitting by rows is that convolution kernels with a vertical size greater than 1 must read adjacent overlapping rows (halo), and the more layers there are, the more overlap there is. In addition, each of the two ANEs reads a complete copy of the weights. For example, after a 3×1 convolution chain on a 16×32 input is split, each ANE reads 9–10 input rows and outputs 8–9 rows. The second is split by output channel. If a layer in the single-ANE program has already been split into several passes because of weight-buffer capacity, and the passes have the same size, the compiler divides these passes evenly between the two ANEs. For example, a 13×1 convolution on an 8×32 input has 2 passes of 128 channels per layer in the single-ANE program; after splitting, each ANE executes one pass. A 5×5 convolution has 4 passes of 64 channels per layer; after splitting, each ANE executes two passes. This method requires no copying and merging 〔HWX〕.

We further disassembled the flow of spatial splitting and verified it in a compilation process of our own with lldb (Section 3.2), obtaining the specific rules for splitting 〔compiler〕. Only the "global refinement" path generates dual-ANE splits. ZinMirSpatialSplitter::Tile enters TileWithGlobalRefinement when the top-level option GlobalRefinementInSpatialSplit is enabled (the default), and it requires that the program be dual-ANE and that the bit at offset 0x73c of the HAL parameter table be set (it is 1 for 2026BaseLine). When this option is turned off, the compiler uses only the single-engine tiling criterion and performs no dual-ANE splitting at all, so the dual-ANE program degrades to executing entirely on ANE0 (Section 5.9).

Spatial splitting occurs at two levels 〔compiler, inferred〕. For subgraphs whose intermediate tensors must be tiled to fit the L2 capacity (Section 9.2.2), a tiling grid of T tiles is first obtained, and the tiles are then assigned to the two ANEs. When the layers in the subgraph have not designated an engine, tile i is assigned to ANE1 when i ≥ T/2 and to ANE0 otherwise, with T/2 rounded down. Therefore, when the number of tiles is odd, the extra tile necessarily goes to ANE1. This is the direct cause of the uneven work partition discussed in Section 10.5 (defect B8). The remaining subgraphs are split by the dual-ANE splitting step into exactly two tiles along one dimension. A tensor of height 1 is split along width; otherwise it is split along height. Cut points are aligned to 256 bytes, that is, to 128 columns of FP16 (or 64 columns when the width is too small). The first tile takes half of the width, rounded up to a multiple of 128. If the remaining part is then less than 128 columns, the rounding is changed to round down. For example, a width of 300 is split into 128 and 172, 375 into 128 and 247, and 640 into 384 and 256.

Refinement uses an iterative scheme based on a worklist of subgraphs. If the current overall splitting scheme has already reached a better result, further refinement stops. Otherwise, the subgraphs are divided further at candidate cut points, and the newly created subgraphs are added back to the worklist until it is empty. In addition, to bound compilation time, the compiler terminates refinement early when the splitting gain is less than 2% and the product of the number of layers and the number of tiles exceeds a preset threshold 〔compiler, inferred〕. Notably, this criterion does not explicitly consider load imbalance, so the compiler may still accept a scheme even when the benefit of splitting is very small. This behavior can be observed in a 16-layer 1×1 convolution chain with 512 channels and height 1. When the input width is 128, the estimated latencies of the unsplit and split schemes are 0.0550 ms and 0.1022 ms, respectively. Splitting significantly increases latency, so the compiler keeps execution on a single ANE. When the width increases to 256, the estimated latencies of the two schemes are 0.10454 ms and 0.10374 ms. Although splitting yields an estimated performance improvement of only about 0.8%, the compiler still accepts the scheme and divides the computation across the two ANEs. This explains the phenomenon in Chapter 10: at width 128, the model uses only a single ANE, while at width 256, both ANEs are enabled.

5.8.4 Cases Without Splitting

Among the 288 shapes, the cases without splitting can all be explained by the criteria above. The first class is where each tile after splitting is too small. All 4×32 shapes are not split, because each ANE would receive only two rows, and the gain is offset by the copy-and-merge latency. The second class is where no usable splitting method exists. The 1×9 to 1×15 convolutions on 8×32 stream their weights within a single TD, so there are no passes to distribute, and splitting by rows would not be faster. The two passes of 3×3 and 9×1 convolutions contain 32 and 224 channels, respectively; these are very unequal and cannot be split by channel, while splitting by rows would require overlapping rows. The two passes of 11×1 convolutions contain 96 and 160 channels, with the same problem. The 3×1 to 7×1 convolutions have no more than 64 KiB of weights per NE, so they have only one pass, and splitting by rows would again require overlapping rows. The third class is where the spatial size is too small. Tensors with very few spatial pixels (such as 1×64 and 1×1), and matrix multiplications with constant weights (M = 1, K = N = 2048, and M = 64, K = N = 1024), have TD sequences only for ANE0 in the dual-ANE program. M = 1 matrix multiplication is the typical shape of the decoding phase of large language models, which implies that matrix multiplication for a single small batch does not become faster because the M6 has two ANEs 〔HWX〕. It is the size of the tensor, not the number of rows, that determines whether splitting occurs. A 1×1 convolution chain with 512 channels and height 1 is not split at widths 64 and 128, but it is split along width at width 256. Likewise, shapes that contain the same 4096 pixels (1×4096, 2×2048, up to 64×64) are all split 〔HWX〕.

The cost model above also does not consider the weight-reading stage that the two ANEs share. Under splitting by rows, each ANE reads a complete copy of the weights, yet the model expects the post-split latency to be halved. Section 10.4 shows that on layers limited by weight reads, such splitting does not yield a speedup (defect B9).

Generating dual-ANE programs requires the additional steps listed in Section 5.3. h18 is one generation earlier than h18g, but the differences between their parameter tables lie mainly in capability switches and a few limit fields (Section 5.4), and the main difference between the two in the compilation workflow is whether dual-ANE programs are generated. Therefore, the difference in compilation time between them can be approximately regarded as the cost of generating dual-ANE programs. When a model is first loaded through Core ML, compilation is a further 2.7 times slower. We used a tool that times only the MLModel loading process (cmload.m), together with the system log of the compiler service and the busy time of each CPU core in IOReport, to compare the compilation time of a 128-step elementwise chain under different methods. The results are shown in Table 5-19 (data: cm_load_vs_compile.txt) 〔timing, IOReport〕.

Table 5-19. Compilation time under different methods (128-step elementwise chain, h18g)

The log of the compiler service shows that only one compilation was performed during Core ML loading, taking 34.05 s, and that the remaining steps of loading took less than 0.3 s in total. The ratio of 34.05 s to 12.65 s is 2.7, which is comparable to the ratio of single-thread performance between S and E cores. Therefore, the main reason compilation becomes slower is that the compiler service runs on E cores, not a difference in compilation options 〔timing, inferred〕. The mechanism is as follows. The launchd configuration of the daemon aned sets ProcessType = Adaptive, so that it runs at background priority when idle. The compiler service (ANECompilerService.xpc) is spawned by aned and inherits this role. Although it is elevated in priority when the client requests compilation (the log shows clientQos=21 threadQos=21), its threads are still scheduled onto E cores. The executable of the compiler service contains no code that binds it to a CPU cluster or actively lowers its priority, so this is the scheduling policy the system applies to XPC services spawned by daemons. The client adjusting QoS can only make compilation slower, not place it on S cores 〔timing, inferred〕. Compilation results are cached, so the above overhead occurs only on first loading.

The compilation cost for real models is even more pronounced. Taking the Whisper large-v3-turbo Core ML package released by WhisperKit as an example, we used cmload.m under a new process name to force first-time loading of its four submodels, because the Core ML and aned compilation caches are keyed by process name. At the same time, we recorded the available disk space and the CPU utilization of the compiler service once per second (tools: whisper_load.sh, whisper_tmp.sh; data: whisper_compile/). On the M6, the mel spectrogram (0.39 s), the context prefill (0.04 s), and the 328 MB text decoder (2.29 s) were all compiled quickly, and when loaded again under the same process name, the compilation results could be reused (0.01–0.08 s). However, the 1.2 GB audio encoder had not finished compiling after 438 s. The disk footprint had increased by about 44 GB, and we aborted the compilation because the available space fell below 15 GB. During compilation, the compiler service, running as root, wrote swap files named anecompiler.swap.* into the cache directory of aned, and its CPU utilization was about 200%. The same encoder, loaded for the first time through Core ML on the M4 (h16g), took only 80 s, with a peak disk footprint of about 1.3 GB and no swap files. Both machines have 16 GB of memory 〔timing〕.

To rule out the influence of Core ML, after compilation had started, we retrieved from the cache directory the model that Core ML handed to the ANE compiler (15849 operations, including 5120 einsum operations, which WhisperKit splits by head and by block to fit the ANE). We then compiled it directly in our own process with anecc (tools: whisper_capture.sh, whisper_anecc.sh). Compiling to h16g and to single-engine h18 both took 41 s, with a peak disk footprint of 3.8 GB. When compiling to h18g, anecc wrote the same swap file into the output directory; after about 220 s, the disk footprint had reached 44 GB, while the peak memory was only about 6 GB 〔timing〕. We then truncated the model to its first N encoder layers (whisper_trunc.py), with the results shown in Table 5-20.

Table 5-20. Compilation cost of the Whisper encoder truncated to its first N layers (anecc)

The disk footprint of h18g is proportional to the number of layers, at about 2.4 GB per layer, which is about 60 times the weights of that layer (about 39 MB). By extrapolation, the complete 32-layer encoder would require about 78 GB. Compilation through Core ML is even slower. In the evaluation, loading through Core ML took about 24 minutes, which is 3–4 times the time extrapolated for anecc (about 6 minutes) and larger than the 2.7-fold difference measured above 〔timing, inferred〕. The 16-layer model was finally compiled, which indicates that this is a resource problem proportional to the number of layers rather than an infinite loop. During compilation, memory was capped at 5–6 GB while the disk kept growing. This indicates that the compiler deliberately stores this data in files, rather than that the system swaps it out when memory is insufficient.

Stack sampling of the h18g compilation of a 4-layer model shows that 97% of the samples lie in ZinMirSplitSpatially → ZinMirSpatialSplitter::TileWithGlobalRefinement → MirOpt::MergeConvolutions → MirOpt::CreateMergedNEConvLayer 〔compiler〕. To find out what the swap file contains, we compiled one encoder layer on the M4 with the same version of the compiler, targeting h18g. The model graph was taken from the real model captured on the M6, while the weights were generated as fake data in the MIL storage format, because the real weights reside only on the M6. The resulting HWX size (73,089,024 bytes) and the peak drop in remaining disk space (2725 MB) both agree with the results on the M6. We then used lldb to record the file creation, deletion, extension, and memory-mapping calls of the compilation process, together with their call stacks (tools: swaptrace_lldb.py, whisper_fakeweights.py; data: swaptrace/) 〔compiler〕.

The results show that the swap file comes from the compiler's file-backed allocator ZinIrFileBacking. When compilation starts, the compiler first creates a file named anecompiler.swap.* in the output directory, then immediately removes its directory entry while keeping the file handle open, and it continuously allocates space through file extension and memory mapping. This space is used mainly to store constant data converted to float32, so FP16 weights occupy about twice the storage after conversion. The allocator supports only space allocation and provides no mechanism for independently freeing allocated regions, so the backing file keeps growing throughout compilation. There were 104 extensions in total, and the file size grew from 8 MB to 2656 MB; the space was released only after compilation finished. Because the directory entry is removed right after creation, this space usage does not appear in the output directory and can be observed only through changes in the system's free disk space 〔compiler〕. Of the 2644 MB of mappings, 2372 MB come from MirOpt::CreateMergedNEConvLayer. During global refinement, one encoder layer generated 101 merged convolution layers, each creating three float32 weight blocks of about 7.7 MB. A large number of convolution merges arises from earlier weight sharding: a large convolution is first split into multiple weight shards by output channel, and during global refinement these shards are further split as independent subgraphs. After graph rewriting, several small convolutions sharing the same input appear within the same spatial block, and MergeConvolutions then merges them back into one larger convolution and generates the corresponding concatenated weights. This process causes significant inflation of the weight data. For a one-layer encoder, the weights generated by merging in each program are about 307 MB, while the original weights are only about 39 MB 〔compiler, inferred〕. By contrast, single-engine h18 does not undergo global refinement, so it does not trigger the above convolution merging and does not produce the corresponding swap file.

Global refinement is also a necessary step for this model to be split across the two ANEs. When the top-level compilation option GlobalRefinementInSpatialSplit is set to false, the h18g compilation of the 4-layer model returns to 8 s with zero disk usage. However, the resulting dual-ANE program contains only the ANE0 TD sequence, which means that the compiler abandoned splitting. Therefore, disabling this option does not solve the problem 〔HWX〕. Even under the default settings, splitting itself is unbalanced. By the sum of exe_cycles estimated by the compiler itself, ANE1 is 1.36–1.48 times ANE0 (for 1 layer, 7074 versus 4783; for 4 layers, 20244 versus 14875), which is 15–19% longer than the critical path under an even split 〔HWX〕. This is the result of several rules in Section 5.8.3 operating together, not a deliberate division of labor. The attention portion has a tile width of 375, and aligning to 128 columns can only split it into 128 and 247. When a tensor of width 1500 is split into three tiles, the extra tile goes to ANE1, becoming 512 and 988. The compiler's cost model does not explicitly consider such imbalance. An attention head group has an estimated gain of −14% when executed on a single engine, but in the dual-ANE split evaluation this cost is simply multiplied by 0.5, so it is still judged to benefit from splitting 〔compiler〕.

When loading through Core ML, two peripheral problems further magnify the compilation cost into a condition in which the whole machine becomes unusable. Ending the loading process does not stop the compiler service, so the swap file keeps growing, and only ending ANECompilerService as root releases it. In addition, the compiler does not check the remaining disk space. During the evaluation, the compiler service filled the system disk until only 121 MB remained. The system then purged the ANE compilation cache, after which the next load of every model required recompilation (Section 14.4). We record the disk cost of global refinement as defect A3, and the continued operation of the compiler service after the client exits, which fills the disk, as defect A4 (Appendix D).

5.12 Summary

This chapter has addressed how compilation arranges work: which operations are handed to the ANE, what the ANE programs look like, and what each of the two engines does. The Core ML segmenter selects a backend for each operation under a fixed cost. An ANE segment must save at least 0.25–0.375 ms before it is selected, and on the basis of the AOT driver, we infer that the M6 retains the cost model of the M4. The ANE compiler generates, for each model, a single-ANE and a dual-ANE program that share one copy of the weights. The programs consist of TD sequences that contain no instructions or branches. The weights of each layer are divided evenly among the 16 NEs by output channel. When the weights exceed 64 KiB per NE, they are split into multiple TDs, or they are read continuously within a single TD. Whether a subgraph is split across the two ANEs is determined by a latency model that assumes the two ANEs do not interfere with each other and does not consider tiles of unequal size. Cut points are aligned to 128 columns, and the extra tile of an odd count is assigned to ANE1. When data must be exchanged, the two ANEs cooperate through a shared scratch buffer and through dedicated words that we infer to be cross-ANE sync records. In terms of compilation cost, the dual-ANE compilation path causes superlinear compilation time, compiler crashes from 387 layers onward, and disk usage proportional to the number of layers (defects B1, A1, and A3).

This chapter establishes only how the compiler arranges work. The questions it leaves open are answered in later chapters: how these programs are selected and submitted at runtime (Chapter 6), and how much the splitting cost model, which ignores shared resources and workload imbalance, actually loses (Chapter 10). The deployment recommendations derived from the conclusions of this chapter are collected in Section 15.2 (Table 15-1).
